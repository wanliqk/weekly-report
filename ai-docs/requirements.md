| V1 规则 | 第二版目标 |

菜单统一改为“我的日报”“我的周报”“设置”，新增“统计”；“用户管理”继续仅 admin 可见和可访问，并增加安全删除入口。周报当前仍使用规则化生成，未来 AI 生成属于 P2，本次不得接入模型、保存模型密钥或发起模型请求。

第二版口径已冻结：默认管理员为 `admin` 且首次登录强制改密；管理员撤销只看必要元数据、不看他人正文；有业务数据用户只能停用；统计按自然日和来源条目计数。改变这些规则必须先更新需求与方案；不可逆迁移仍需完成实现阶段的旧库副本验证后才能执行。

## 1. 产品目标

建设一套面向 Windows 桌面的多用户日报周报管理系统。用户可在同一工作日期记录多篇日报条目，经提交后由日期级归档汇总为一篇正式日报；系统按自然周汇总正式日报生成可编辑周报，并支持正式日报 Excel 导出。系统保留企业微信占位及未来 AI 周报扩展边界，但当前不连接任何企业微信或大模型接口。

## 2. 用户与权限

| 角色 | 能力 | 数据边界 |
|---|---|---|
| `user` | 管理自己的模板、日报、周报、导出和个人设置 | 仅本人数据 |
| `admin` | 具备普通用户能力；用户增删改查、重置密码、撤销尚未归档的已提交日报条目和执行整库手动备份 | 撤销提交只开放必要元数据，不查看他人正文；其他个人业务仍按所有者隔离 |

系统首次启动时创建首个普通用户，并在同一事务自动创建用户名固定为 `admin` 的默认管理员；管理员初始密码固定为 `admin123`（与首位用户输入的密码无关），两个账号密码分别哈希保存。默认管理员首次登录必须改密，完成前不能使用业务 API。必须阻止禁用、降级或删除最后一个有效管理员。

## 4. 核心业务规则

### 4.1 日报

1. 同一用户、同一 `work_date` 在日期未归档时允许创建多篇日报条目，不设置业务篇数上限。
2. 日报条目只允许草稿和已提交两种可操作阶段：草稿可编辑/删除，提交时由服务端按模板快照校验，已提交只读。
3. 普通用户不能撤销提交；admin 可将尚未归档的已提交条目撤回草稿，并记录操作者、时间和原因。
4. 日期级归档只接收当天全部已提交条目。当前基线为有草稿时阻止归档，至少有一篇已提交且无草稿时才可执行。
5. 归档按稳定顺序无损保留每篇来源边界，原子生成该用户该日期唯一的正式日报并关闭日期；重复/并发归档不能生成第二篇。
6. 日期归档后不得新建条目、删除来源、撤销提交或修改正式日报；第二版仍不支持撤销日期归档。
7. 可补写历史和未来日期，但任何日期一旦归档均禁止继续创建。
8. 每篇条目创建时固化模板版本和完整字段快照；后续模板变更不得改变历史内容。
9. “提交后自动归档”被第二版停用/移除，提交动作不得自动关闭日期。

### 4.2 模板

1. 每个用户一套当前模板，发布新配置时生成不可变版本，不原地修改历史版本。
2. 默认核心字段为“今日工作内容”和“明日工作计划”；可改显示名称和顺序，不可删除，且至少启用一个核心字段。
3. V1 字段类型：单行文本、多行文本、数字、日期、单选、多选；不含附件。
4. `field_key` 创建后不可变，显示名称变化不影响导出列合并和历史追溯。

### 4.3 周报

1. 自然周固定为 Asia/Shanghai 周一至周日；`week_start` 必须是周一。
2. 同一用户、同一 `week_start` 只保留一份当前周报。
3. 只汇总该周每个完成日期唯一的当日归档日报；草稿、已提交未归档条目和归档来源条目不直接参与汇总。
4. 周报包含按日期汇总的自动内容，以及“本周补充、下周计划、问题风险”编辑区。
5. 人工编辑不反写日报。重新生成必须显式确认，并覆盖当前自动内容和人工编辑内容。

### 4.4 导出

1. 每个完成日期的当日归档日报作为一份正式记录，只允许当前用户的正式日报进入导出文件；来源条目不得重复导出为正式日报。
2. 基础列在前，动态字段按稳定 `field_key` 合并；同名标签追加字段短标识。
3. 显式选择中含不可导出记录时整体拒绝并列出问题 ID，不静默忽略。

## 6. 关键验收场景

- Given 尚无用户，When 首次初始化，Then 原子创建首个普通用户、默认 admin 及各自默认数据，重复/并发初始化不产生第二组账号。
- Given 密码已修改或账号已禁用，When 使用旧 Token，Then 返回 Token 失效且不泄露数据。
- Given 同日已有草稿或已提交条目且日期未归档，When 再次创建，Then 生成新的独立草稿。
- Given 日期已经归档，When 尝试创建新条目，Then 服务端拒绝且不产生数据。
- Given 草稿缺少必填字段，When 提交，Then 保持草稿并返回字段级错误。
- Given admin 撤销尚未归档的已提交条目，When 操作成功，Then 条目回到草稿、正文保留且所有者可见撤销原因。
- Given 当天仍有草稿，When 用户请求日期级归档，Then 系统阻止并提示先提交或删除草稿。
- Given 当天有多篇已提交且无草稿，When 用户确认日期级归档，Then 原子生成一篇正式日报、保留全部来源并关闭日期。
- Given 模板发布了新版本，When 查看旧日报，Then 字段、顺序、标签和值仍按旧快照展示。
- Given 导出跨多个模板版本，When 生成 Excel，Then 所有历史字段按 `field_key` 合并且值不丢失。
- Given 跨年自然周，When 生成周报，Then 周范围和日报归属正确。
- Given 周报已被人工修改，When 未确认重生成，Then 系统拒绝覆盖。
- Given 当前月截至今天有 5 个完成日期和 7 个自然日，When 查看统计，Then 完成率为 71.4%，未来日期不计入分母。
- Given 用户访问他人资源 ID，When 查询或修改，Then 返回 404 且不泄露内容。

## 9. 企业微信日报反向同步增量（CR-20260808-02）

> 状态：需求与技术方案已确认；后端数据层/凭证桥/协议 Client/字段 Mapper/连接与同步编排 Service/公开与 Main-only API（`WECOM-00..06`）均已实现并通过独立审查，renderer 交互（`WECOM-07`）和全链路验收发布（`WECOM-08`）仍未开始；当前产品仍为企业微信占位（`wecom_sync=false`），具体事实以 `progress.md`/`task.md` 为准。

- 当前用户可通过受控网页登录连接自己的企业微信账号，手动把本人已归档的日期级正式日报同步到一个启用中的企业微信日报模板。
- 同步源只读 `daily_report_days.archive_snapshot_json`；草稿、未归档日期、管理员代看的他人日报不得同步。
- 目标字段固定为日期、今日工作内容、明日工作计划；本地动态字段按稳定 `field_key` 配置，`today_work`/`PROJECT_LIST` 默认映射今日，`tomorrow_plan` 默认映射明日，未映射非空字段阻止提交。
- Cookie jar 只由 Electron Main 通过 `safeStorage` 加密保存，不进入 SQLite、renderer、日志、备份或错误响应。
- 同一正式日报向同一目标成功后不得重复提交；可能已受理但无法确认时标记 `uncertain` 并禁止自动重试。
- 首版不做自动同步、历史批量补发、从企业微信导入、附件/其他事项、多目标并行或 admin 同步他人日报。
- 企业微信内部接口属于不稳定协议；结构变化、认证失效、重复候选和结果不确定必须分别阻断并给出可操作反馈。

完整范围、字段转换和验收标准以 `docs/需求理解.md` 的 CR-20260808-02 章节为准。

## 10. 项目列表子列扩展（CR-20260812-01）

- `PROJECT_LIST` 条目固定为 10 个子列，顺序是：类别、工作项目、工作步骤、权重、预计完成时间节点、实际完成时间、责任人、协助人、所需资源支持、实际完成情况及解决措施。
- 只有工作项目、工作步骤必填。renderer 新建行默认：类别“重要”、预计/实际完成时间“当日”、责任人取当前登录用户 `display_name`、完成情况“已完成”；权重、协助人、所需资源支持默认空。完全未触碰的整套默认行保存前过滤。
- 历史 JSON 缺少字段时由 Pydantic 补结构默认值，但缺少 owner 时保持空字符串，不按当前查看者回填；不新增数据库迁移，Excel 导出按上述 10 列输出。
- 企业微信今日工作映射仍只同步工作项目和工作步骤，类别、权重及其余跟踪字段只在本地使用。
