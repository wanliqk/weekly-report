# 个人日报周报管理系统技术方案（第一版）

> 2026-08-07 需求变更提示：`docs/需求理解.md` 已新增 CR-20260807-01，改变了同日唯一、日报状态机、自动归档、首次初始化、管理员权限和周报来源，并新增统计模块。本文仍可用于说明当前 V1 实现，但不再是第二版目标方案；完成新的方案设计、数据迁移和接口评审前不得按本文旧状态机继续扩展实现。

## 1. 技术方案概述

系统采用“Electron 桌面壳 + Vue 3 渲染进程 + FastAPI 本地服务 + SQLite 本地数据库”的单机桌面架构。

- Electron 主进程负责单实例、窗口、应用数据目录、FastAPI 子进程启停、下载保存对话框和应用退出清理。
- Vue 3 渲染进程负责登录、日报、模板、周报、用户管理等界面，仅通过 RESTful API 访问业务数据。
- FastAPI 是唯一业务入口，负责认证、权限、状态机、模板快照、周报生成、Excel 导出和数据库事务。
- SQLite 数据库由 FastAPI 进程独占访问，文件存放在 Electron 的 `userData` 目录，不放在安装目录。
- 开发阶段使用 `uv` 管理 Python、虚拟环境和锁文件；发布时将后端打包为独立 sidecar，目标机器无需安装 Python 或 uv。

第一版建议以 Windows 10/11 x64 为验收平台。Electron/electron-vite 工具链可支持更多桌面平台，但 Python sidecar 必须按目标操作系统分别构建，跨平台发布不作为第一版验收项。

## 2. 需求回顾与设计范围

### 2.1 第一版范围

- 首次启动创建管理员，之后使用用户名和密码登录。
- 支持 `admin`、`user` 两种角色；管理员管理账号，但默认无权查看其他用户的日报和周报。
- JWT 有效期 24 小时；修改密码、禁用账号后，已有 Token 立即失效。
- 日报按“草稿 → 已提交 → 已归档”流转，并支持用户级“提交后自动归档”设置。
- 用户可补写历史或未来日期；同一用户同一工作日期只允许一份日报。
- 模板版本不可变，新日报保存模板快照，历史日报不受模板修改影响。
- 只导出已归档日报；动态字段按稳定字段标识合并为 Excel 列。
- 周报按 Asia/Shanghai 时区的周一至周日生成，只汇总已归档日报。
- 企业微信仅显示“功能暂未开放”，不实现授权和网络请求。

### 2.2 第一版明确采用的默认决策

需求中的未决项按以下规则落地，后续可在实现前调整：

| 决策项 | 第一版选择 |
|---|---|
| 归档撤回 | 不支持；归档后只读 |
| 默认核心字段 | “今日工作内容”“明日工作计划”可改显示名称和顺序，但不能删除；至少启用一个核心字段 |
| 模板字段类型 | 单行文本、多行文本、数字、日期、单选、多选；第一版不支持附件 |
| 周报结构 | 按工作日期依次汇总字段，附独立的“本周补充/下周计划/问题风险”可编辑区，不做 AI 归并 |
| 周报重复生成 | 同周只保留一份；存在周报时默认返回现有记录，重新生成必须显式确认，并覆盖当前自动内容及当前编辑内容 |
| Excel 结构 | 每份日报一行；基础字段在前，动态模板字段按字段稳定标识合并；同名字段追加短标识消歧 |
| 数据保留 | 默认永久保留；迁移前自动备份，提供手动备份能力，第一版不实现云同步 |

## 4. 总体架构

```text
┌──────────────── Electron 应用 ────────────────┐
│                                               │
│  Vue 3 Renderer                               │
│  页面 / Pinia / API Client                    │
│          │ HTTPS-like local contract          │
│          │ HTTP + Bearer JWT + runtime header │
│          ▼                                    │
│  FastAPI sidecar (127.0.0.1:动态端口)         │
│  Router → Service → Repository → SQLite       │
│          │                                    │
│          ├─ Excel 临时文件                    │
│          └─ Alembic / 备份                    │
│                                               │
│  Electron Main / Preload                      │
│  单实例、进程管理、路径、令牌安全存储、下载   │
└───────────────────────────────────────────────┘
```

### 4.1 启动与退出流程

1. Electron 获取单实例锁和 `app.getPath('userData')`。
2. 主进程选择空闲回环端口，生成每次启动随机的 `runtime_secret`。
3. 开发环境执行 `uv run python -m app`；生产环境执行安装包内的 FastAPI sidecar。
4. 通过环境变量或启动参数传递数据库目录、端口、日志目录和运行期密钥，敏感值不得写入日志。
5. FastAPI 执行迁移、初始化默认配置，监听 `127.0.0.1`，健康检查成功后 Electron 才显示业务窗口。
6. preload 只向渲染进程暴露 API 基址、运行期请求头、Token 安全存取和文件保存等最小能力。
7. 应用退出时先要求 FastAPI 停止接收请求并关闭数据库连接，超时后再终止子进程，避免残留进程。

固定要求：FastAPI 禁止绑定 `0.0.0.0`；端口不得硬编码；只允许一个后端实例写同一个 SQLite 文件。

### 4.2 开发与生产差异

| 场景 | 前端 | 后端 | 数据目录 |
|---|---|---|---|
| 开发 | Vite dev server | `uv run uvicorn`，支持热重载 | 仓库下 `.local-data/`，加入 `.gitignore` |
| 生产 | Electron 内置静态资源/自定义协议 | PyInstaller sidecar | Electron `userData/data/` |

生产包不能依赖用户机器上的 Python、uv、Node.js 或全局环境变量。

## 7. 前端设计

### 7.1 页面与路由

| 路由 | 页面 | 权限 |
|---|---|---|
| `/setup` | 首次创建管理员 | 仅未初始化状态 |
| `/login` | 登录 | 匿名 |
| `/daily` | 日报列表、筛选 | 登录用户 |
| `/daily/new` | 选择日期并创建日报 | 登录用户 |
| `/daily/:id` | 日报查看/编辑/提交/归档 | 记录所有者 |
| `/templates` | 当前日报模板配置 | 登录用户 |
| `/weekly` | 周报列表、周选择 | 登录用户 |
| `/weekly/:id` | 周报详情和编辑 | 记录所有者 |
| `/settings` | 自动归档等个人设置 | 登录用户 |
| `/admin/users` | 用户管理 | admin |

### 7.2 状态管理

- `authStore`：当前用户、内存中的 access token、登录/退出。
- `runtimeStore`：后端启动状态、API 基址、能力开关。
- 业务列表查询条件尽量放入 URL query，避免全局 store 堆积服务端数据。
- Axios 响应拦截器解包 `data`，按 `code` 映射提示；HTTP 401 清理 Token 并跳转登录。
- 保存日报时发送 `version` 做乐观并发校验；409 时提示重新载入，避免旧页面覆盖新内容。

### 7.3 Electron 安全基线

- `contextIsolation: true`、`nodeIntegration: false`、`sandbox: true`。
- preload 使用 `contextBridge` 白名单 API，禁止暴露任意 IPC、文件路径或命令执行。
- 禁止加载任意远程页面；生产使用应用自定义协议并设置 CSP。
- 开发和生产分别配置精确 CORS 白名单，不使用 `allow_origins=['*']`。
- JWT 不写普通 `localStorage`；由主进程通过 Electron `safeStorage` 加密落盘，renderer 只在运行期持有。
- 外部链接必须校验 `https` 域名后交给系统浏览器打开。

## 8. API 通用规范

### 8.1 基本约定

- 基础路径：`/api/v1`。
- 请求/响应使用 UTF-8 JSON，字段采用 `snake_case`；前端生成共享 TypeScript 类型或在适配层转换。
- 时间使用 ISO 8601 且带时区，例如 `2026-08-04T20:26:00+08:00`；工作日期使用 `YYYY-MM-DD`。
- 列表默认按业务日期降序、ID 降序稳定排序。
- 认证头：`Authorization: Bearer <token>`。
- 所有本地 API 额外校验 `X-Runtime-Secret`，该值仅用于限制其他本机进程误调用，不能替代用户认证。
- 每个响应带 `X-Request-Id`，日志按请求 ID 关联，但不记录密码、Token 和日报正文。

### 8.2 统一返回结构

成功响应：

```json
{
  "code": 0,
  "msg": "success",
  "data": {}
}
```

分页响应：

```json
{
  "code": 0,
  "msg": "success",
  "data": {
    "items": [],
    "page": 1,
    "page_size": 20,
    "total": 0
  }
}
```

错误响应：

```json
{
  "code": 40901,
  "msg": "该工作日期已存在日报",
  "data": {
    "existing_report_id": "01J..."
  }
}
```

HTTP 状态码表达协议结果，`code` 表达稳定的业务错误；成功固定为 0。FastAPI 的参数校验异常也转换为上述结构。Excel 文件流是统一 JSON 包装的唯一例外；其失败响应仍返回结构化 JSON。

### 8.3 错误码规划

| code | HTTP | 含义 |
|---:|---:|---|
| 40001 | 400 | 参数或业务规则校验失败 |
| 40101 | 401 | 用户名或密码错误 |
| 40102 | 401 | Token 无效、过期或版本失效 |
| 40301 | 403 | 角色权限不足 |
| 40302 | 403 | 资源不属于当前用户 |
| 40401 | 404 | 资源不存在 |
| 40901 | 409 | 同日期日报已存在 |
| 40902 | 409 | 非法日报状态流转 |
| 40903 | 409 | 同自然周周报已存在 |
| 40904 | 409 | 乐观锁版本冲突 |
| 42201 | 422 | 模板必填字段缺失或值类型不匹配 |
| 50001 | 500 | 内部错误 |
| 50301 | 503 | 数据库繁忙或服务暂不可用 |

## 9. RESTful API 设计

以下接口除首次初始化、登录和健康检查外均需 JWT。

### 9.1 系统与认证

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/health` | 后端存活状态，不返回敏感信息 |
| GET | `/api/v1/system/bootstrap-status` | 是否需要首次初始化 |
| POST | `/api/v1/system/bootstrap-admin` | 仅用户表为空时原子创建首个 admin |
| POST | `/api/v1/auth/login` | 用户名密码登录，返回 24 小时 access token |
| GET | `/api/v1/auth/me` | 当前用户信息和权限 |
| PUT | `/api/v1/auth/password` | 修改密码并增加 `token_version` |
| POST | `/api/v1/auth/logout` | 客户端清 Token；第一版不维护 Token 黑名单 |

登录请求示例：

```json
{
  "username": "admin",
  "password": "********"
}
```

JWT 至少包含 `sub`、`role`、`ver`、`iat`、`exp`、`jti`。每次鉴权读取用户的启用状态和 `token_version`；密码修改、管理员重置密码或禁用用户后，旧 Token 立即失效。

### 9.2 用户管理

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/users` | admin 分页查询用户 |
| POST | `/api/v1/users` | admin 创建用户并初始化默认模板 |
| GET | `/api/v1/users/{id}` | admin 查看账号元数据，不含业务内容 |
| PATCH | `/api/v1/users/{id}` | 修改显示名、角色、启用状态 |
| PUT | `/api/v1/users/{id}/password` | admin 重置密码并使旧 Token 失效 |

为保护个人记录，管理员接口不提供“查看他人日报/周报”的能力。系统必须阻止禁用最后一个有效管理员或将其降级。

### 9.3 日报模板

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/report-templates/current` | 获取当前模板及版本字段 |
| PUT | `/api/v1/report-templates/current` | 校验后发布新版本，不原地修改旧版本 |
| GET | `/api/v1/report-templates/versions` | 查询本人的历史版本摘要 |

模板字段结构：

```json
{
  "field_key": "uuid-stable-key",
  "label": "今日工作内容",
  "description": "",
  "field_type": "textarea",
  "required": true,
  "enabled": true,
  "sort_order": 10,
  "options": []
}
```

`field_key` 创建后不可变，重命名仍保留该标识；单选/多选必须提供非空且不重复的选项。

### 9.4 日报

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/daily-reports` | 按 `date_from`、`date_to`、`status` 分页查询 |
| POST | `/api/v1/daily-reports` | 按工作日期和当前模板创建草稿 |
| GET | `/api/v1/daily-reports/{id}` | 获取详情、模板快照和内容 |
| PATCH | `/api/v1/daily-reports/{id}` | 仅草稿可保存内容，必须携带 `version` |
| POST | `/api/v1/daily-reports/{id}/submit` | 校验必填项并提交；可按设置同事务自动归档 |
| POST | `/api/v1/daily-reports/{id}/archive` | 仅已提交状态可归档 |

创建请求：

```json
{
  "work_date": "2026-08-04"
}
```

保存请求：

```json
{
  "version": 3,
  "content": {
    "uuid-field-1": "完成日报模块设计",
    "uuid-field-2": "开始搭建工程"
  }
}
```

创建时在同一事务中读取当前模板版本、写入模板快照和空内容。唯一约束冲突返回 40901 及已有日报 ID。服务端必须按快照校验字段，不信任前端传来的标签、类型或必填配置。

### 9.5 Excel 导出

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/daily-report-exports` | 根据日报 ID 或筛选条件创建导出文件，返回 export ID |
| GET | `/api/v1/daily-report-exports/{id}` | 查询导出状态和统计 |
| GET | `/api/v1/daily-report-exports/{id}/file` | 下载 `.xlsx` 二进制文件 |

导出创建参数只能二选一：`report_ids` 或 `filter`。后端再次按当前用户和 `archived` 状态过滤；如果明确勾选中存在不可导出的记录，整体返回 40001 并列出 ID，不静默混入。

列规划：`工作日期、状态、创建时间、提交时间、归档时间、动态字段...`。动态字段按 `field_key` 合并，标题采用对应快照中最近的标签；标签重复时追加字段短 ID。临时文件在成功下载、24 小时过期或应用启动清理时删除。

### 9.6 周报

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/weekly-reports/availability?week_start=YYYY-MM-DD` | 返回周范围、已归档及未归档日报日期 |
| GET | `/api/v1/weekly-reports` | 按周范围分页查询 |
| POST | `/api/v1/weekly-reports` | 生成周报；无归档日报时也可生成空白周报 |
| GET | `/api/v1/weekly-reports/{id}` | 获取当前内容、自动基线和来源日报 |
| PUT | `/api/v1/weekly-reports/{id}` | 保存人工编辑内容，必须携带 `version` |
| POST | `/api/v1/weekly-reports/{id}/regenerate` | `confirm_overwrite=true` 时重新汇总并覆盖内容 |

生成请求：

```json
{
  "week_start": "2026-08-03"
}
```

后端校验 `week_start` 必须为 Asia/Shanghai 的周一，并计算 `week_end`。生成事务中锁定逻辑范围、查询已归档日报、写入来源关系和来源快照。同周唯一约束避免重复点击生成两份周报。

周报内容使用结构化 JSON，不存 HTML：

```json
{
  "days": [
    {
      "work_date": "2026-08-04",
      "daily_report_id": "01J...",
      "fields": [
        {"field_key": "...", "label": "今日工作内容", "value": "..."}
      ]
    }
  ],
  "supplement": "",
  "next_week_plan": "",
  "risks": ""
}
```

`generated_content` 保存自动生成基线，`content` 保存当前可编辑内容。重新生成前若 `content != generated_content`，API 必须要求显式确认；第一版确认后覆盖，不提供恢复，界面需要醒目提示。

### 9.7 设置与能力开关

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/settings/me` | 获取当前用户设置 |
| PATCH | `/api/v1/settings/me` | 修改提交后自动归档等设置 |
| GET | `/api/v1/capabilities` | 返回 `wecom_sync: false` 等功能状态 |

## 11. 核心业务规则与事务

### 11.1 日报状态机

```text
draft --submit--> submitted --archive--> archived
  └--submit + auto_archive_on_submit-----------> archived
```

- `draft`：允许修改内容。
- `submitted`：第一版不允许再编辑，只能归档。
- `archived`：完全只读，可用于 Excel 和周报。
- 所有状态转换必须以条件更新或事务内复查当前状态，重复请求不能重复改变时间戳。
- 自动归档时，提交校验、写 `submitted_at`、写 `archived_at` 和最终状态必须在同一事务完成。

### 11.2 所有权隔离

每个 Repository 查询都强制携带 `current_user.id`，禁止先按资源 ID 查询后再在 API 层判断。对无权资源统一返回 404 可减少资源枚举；40302 仅在明确业务场景使用。

### 11.3 SQLite 设置

连接初始化执行：

```sql
PRAGMA journal_mode=WAL;
PRAGMA foreign_keys=ON;
PRAGMA busy_timeout=5000;
PRAGMA synchronous=NORMAL;
```

- 保持单个 FastAPI worker；SQLite 场景不得启动多个 Uvicorn workers。
- 写操作使用短事务；Excel 生成先读取所需快照，再在事务外写文件。
- 捕获 `SQLITE_BUSY` 并转换为 50301，前端允许安全重试。
- 迁移前执行 WAL checkpoint 并备份数据库；迁移失败则停止启动，不带病运行。

## 12. 日志、备份与异常恢复

- 日志目录：`userData/logs/`，按天轮转并限制保留天数。
- 日志记录级别、模块、请求 ID、错误类型和耗时；禁止记录密码、JWT、runtime secret、完整日报/周报正文。
- 数据目录：`userData/data/weekly-report.db`；导出临时目录：`userData/temp/exports/`；备份目录：`userData/backups/`。
- 每次数据库结构迁移前创建带时间戳备份，默认保留最近 10 份；删除旧备份前先校验路径位于备份目录。
- 提供“备份数据库”桌面操作时，先 checkpoint，再由后端生成一致性备份，通过 Electron 保存对话框复制到用户选择位置。
- 后端启动失败、迁移失败或健康检查超时时，Electron 展示可操作错误页和日志目录入口，不进入业务页面。

## 15. 关键设计决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| Electron 与后端通信 | 回环地址 REST API | 保持前后端边界清晰，便于独立测试和未来迁移 Web |
| electron-vite 使用边界 | 只作 Electron 三端开发/构建工具 | 避免 Node 与 Python 两套业务服务和数据库访问 |
| 后端运行 | 单 sidecar、单 worker | 符合 SQLite 写入模型并简化生命周期 |
| API 返回 | HTTP 状态 + `{code,msg,data}` | 同时保留 REST 语义和稳定业务错误处理 |
| 模板历史 | 不可变模板版本 + 日报 JSON 快照 | 历史稳定，同时保留来源版本可追溯性 |
| 动态内容 | 结构化 JSON | 字段变化频繁，不需要按字段值做复杂检索；避免频繁改表 |
| 周报来源 | 仅 archived | 与正式记录口径一致 |
| 周报重生成 | 显式确认后覆盖 | 第一版实现简单且不会静默丢失人工修改；版本历史留待 P2 |
| 本地认证 | 24h JWT + token_version | 满足无状态接口和密码修改后立即失效 |
| Token 存储 | Electron safeStorage | 比 renderer localStorage 更适合桌面敏感信息 |
| 导出 | 任务记录 + 二进制下载 | 可展示处理中状态，并保持普通 API 统一 JSON |

## 16. 风险与待确认项

| 风险/待确认 | 当前处理 | 影响 |
|---|---|---|
| 是否首发 macOS/Linux | 默认仅 Windows 10/11 x64 | 若需要跨平台，需增加各平台 sidecar 构建、签名和 CI |
| 周报重新生成策略 | 显式确认后覆盖 | 如需版本对比/恢复，应增加版本表和 UI，工作量上升 |
| 模板字段类型 | 第一版六种、无附件 | 附件会引入文件生命周期、备份和导出设计 |
| 管理员数据权限 | 只能管账号，不能看他人内容 | 若业务要求管理员审阅，需新增明确权限而非复用 admin |
| 本地数据加密 | 第一版密码加密、Token 安全存储，数据库不整体加密 | 如要求磁盘泄露防护，需评估 SQLCipher、密钥托管和备份恢复 |
| electron-vite/Electron 上游变化 | 由 `package-lock.json` 固定，升级需评审 | 不固定版本会导致构建、sandbox 和打包规则漂移 |
| PyInstaller 误报/体积 | 做签名、白名单说明和干净机测试 | Python sidecar 可能增大安装包并触发杀软误报 |

其中“首发平台、周报覆盖策略、管理员是否可查看用户内容、是否要求数据库整体加密”建议在代码实现前确认；若没有补充，按本文默认决策实现。

## 2026-08-07 第二版增量技术方案（CR-20260807-01）

> 方案状态：设计已完成，等待用户确认；当前代码仍是 V1 行为
> 需求依据：本仓库 `docs/需求理解.md` 中“日报、周报、账户与统计需求变更（第二版增量）”
> 兼容目标：保留 Electron + Vue 3 + FastAPI + SQLite 架构、安全边界和现有历史数据

### 1. 冻结的产品口径

本次按需求稿中的推荐基线实现，后续若改变其中任一项，必须重新评审数据库、权限或统计契约：

1. 默认管理员用户名固定为 `admin`，首次普通用户不得使用大小写归一化后等于 `admin` 的用户名。
2. 默认管理员初始密码与首次普通用户密码相同，但分别执行 Argon2id 哈希；管理员首次登录后必须先修改密码，完成前不能进入业务页面或调用业务 API。
3. 管理员撤销提交时只查看账号、日期、状态、条目标识、版本和提交时间等必要元数据，不能查看其他用户日报正文或模板快照。
4. 日期级归档前必须处理完当天所有草稿；只要仍有草稿就阻止归档，不允许静默忽略。
5. 只有完全没有业务记录的账号可以物理删除；已有日报、周报、导出等业务记录的账号只能停用。
6. 月份完成率按自然日计算，周末计入；“已写日报篇数”按已提交条目和归档来源条目计算，日期级正式日报不重复加一。
7. 当前连续记录天数按完成日期计算：今天完成则从今天向前；今天未完成但昨天完成则从昨天向前；最近完成早于昨天则为 0。

### 2. 范围与非目标

本次交付同日多条目、草稿删除、管理员撤销、日期级正式归档、双账号初始化、安全删除、菜单改名和个人统计，并适配现有周报与 Excel 导出。

以下内容仍不在本次范围：AI 模型接入或密钥保存、企业微信真实同步、日期归档撤回、归档结果人工编辑、级联删除用户全部业务数据、管理员查看他人正文、组织级统计、工作日/节假日配置。未来 AI 周报必须作为独立能力，通过显式设置启用，并只读取当前用户可见的日期级正式日报。

第二版在 FastAPI 内增加“日报日期聚合”“管理员日报操作”“个人统计”“审计事件”能力，不新增 Node 业务层，也不扩大 preload 接口：


### 4. 领域术语与状态模型

- **日报条目**：`daily_reports` 中的一条工作记录，属于某个用户和工作日期。日期未归档时允许创建多条。
- **日报日期容器**：`daily_report_days` 中的一行，唯一标识某用户某日期，并作为该日期所有写操作的并发互斥点。
- **当日归档日报**：日期容器归档后保存的不可变正式快照；同一用户同一日期最多一份。
- **来源条目**：已经进入当日归档日报的条目。数据库中仍保留为 `archived` 只读记录，用于追溯，但不再独立进入周报、导出或完成天数统计。

条目状态仍使用三值以兼容历史数据，但归档动作从“单篇归档”改为“日期级批量归档”：

```text
draft --用户提交--> submitted --日期级归档事务--> archived
  ^                        |
  +---- admin 撤销提交 ----+

draft --所有者删除--> 物理删除
```

日期容器状态：

```text
open --日期级归档事务--> archived
```

约束如下：

- `open` 日期允许新建条目；`archived` 日期禁止创建、保存、删除、提交和撤销。
- 用户只能修改和删除自己的 `draft`；用户只能提交自己的 `draft`；普通用户不能撤销 `submitted`。
- admin 只能撤销 `open` 日期下的 `submitted`，撤销后正文和模板快照保持不变、`submitted_at` 清空、版本递增。
- 日期级归档要求至少一个 `submitted` 且没有 `draft`，将全部 `submitted` 原子改为 `archived`，并同时固化正式快照和关闭日期。
- `archived` 日期和来源条目永久只读；第二版没有撤销日期归档的反向状态。
- V1 的 `auto_archive_on_submit` 被移除；提交动作永远只到 `submitted`。

### 5. 数据模型

#### 5.1 `daily_report_days`：日期容器与正式日报

新增表：

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `VARCHAR(26)` | PK | ULID；迁移历史数据时复用原日报 ID |
| `user_id` | `VARCHAR(26)` | FK `users.id` RESTRICT, NOT NULL | 所有者 |
| `work_date` | `DATE` | NOT NULL | Asia/Shanghai 业务日期 |
| `status` | `VARCHAR(16)` | CHECK `open/archived` | 日期是否关闭 |
| `archive_snapshot_json` | `TEXT` | nullable | 归档后不可变的正式日报快照 |
| `source_count` | `INTEGER` | NOT NULL, default 0, CHECK >= 0 | 正式日报的来源条目数 |
| `archived_by` | `VARCHAR(26)` | FK `users.id` RESTRICT, nullable | 执行归档的所有者账号 |
| `archived_at` | `DATETIME` | nullable | UTC 归档时间 |
| `version` | `INTEGER` | NOT NULL, default 1, CHECK > 0 | 日期级乐观锁/串行化版本 |
| `created_at`/`updated_at` | `DATETIME` | NOT NULL | UTC 审计时间 |

数据库约束：

- `UNIQUE(user_id, work_date)` 是同一日期唯一正式日报的最终防线。
- `open` 行要求 `archive_snapshot_json/archived_by/archived_at` 为空且 `source_count=0`。
- `archived` 行要求快照、归档人和归档时间非空且 `source_count>0`。
- 索引 `ix_daily_report_days_user_date(user_id, work_date DESC, id DESC)` 支持月历、日期详情和统计。
- 索引 `ix_daily_report_days_user_status_date(user_id, status, work_date DESC)` 支持周报、导出和完成日期查询。

#### 5.2 `daily_reports`：多篇来源条目

重建现有表，取消 `UNIQUE(user_id, work_date)`，改为通过日期容器确定所有者和日期：

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `VARCHAR(26)` | PK | 条目 ULID |
| `day_id` | `VARCHAR(26)` | FK `daily_report_days.id` RESTRICT, NOT NULL | 所属日期容器 |
| `client_request_id` | `VARCHAR(64)` | UNIQUE, NOT NULL | 创建幂等键；历史行取原条目 ID |
| `status` | `VARCHAR(16)` | CHECK `draft/submitted/archived` | 条目状态 |
| `template_version_id` | `VARCHAR(26)` | FK RESTRICT, NOT NULL | 创建时模板版本 |
| `template_snapshot_json` | `TEXT` | NOT NULL | 完整不可变模板快照 |
| `content_json` | `TEXT` | NOT NULL | 结构化内容 |
| `version` | `INTEGER` | NOT NULL, CHECK > 0 | 条目乐观锁 |
| `submitted_at` | `DATETIME` | nullable | 最近一次有效提交时间；撤销时清空 |
| `archived_at` | `DATETIME` | nullable | 随日期归档写入 |
| `created_at`/`updated_at` | `DATETIME` | NOT NULL | UTC 时间 |

所有权查询必须连接 `daily_report_days` 并在 Repository 层同时约束 `daily_report_days.user_id=current_user.id`。`client_request_id` 由 renderer 在用户点击创建时生成并在重试时复用；同一键重复请求返回既有条目，不再创建第二条，不同键即使同日也创建独立草稿。

索引 `ix_daily_reports_day_status_submit(day_id, status, submitted_at, id)` 支持日期列表、稳定归档排序和草稿/已提交计数。状态时间约束为：`draft` 的 `submitted_at/archived_at` 均为空；`submitted` 只有 `submitted_at`；`archived` 两者均非空。

#### 5.3 正式归档快照

`archive_snapshot_json` 使用带版本号的结构，按 `submitted_at ASC, daily_report_id ASC` 固化来源顺序：

```json
{
  "schema_version": 2,
  "work_date": "2026-08-07",
  "entries": [
    {
      "daily_report_id": "01...",
      "submitted_at": "2026-08-07T09:00:00+00:00",
      "template_version_id": "01...",
      "template_snapshot": [],
      "content": {}
    }
  ]
}
```

正式快照无损保留每篇来源边界、模板标签、字段顺序和值；不同条目中相同 `field_key` 不在归档时合并。快照写入前必须通过版本化 Pydantic schema 校验，读取未知 `schema_version` 时明确失败，不以任意字典继续处理。

#### 5.4 `weekly_report_sources`

将 `daily_report_id` 改为 `daily_report_day_id`，外键指向 `daily_report_days.id`；主键变为 `(weekly_report_id, daily_report_day_id)`。周报只关联日期级正式日报，来源详情先打开当日归档日报，再由其快照追溯条目。

#### 5.5 `admin_audit_events`

新增通用管理员审计表，首批记录 `daily_submission_revoked` 与 `user_deleted`：

| 字段 | 说明 |
|---|---|
| `id` | ULID 主键 |
| `action` | 受 CHECK 限制的动作类型 |
| `actor_user_id` | 操作者 FK，账号删除后允许 `SET NULL` |
| `actor_username_snapshot` | 操作时用户名快照 |
| `target_type`/`target_id` | 目标类型和标识，不建目标外键，以便草稿后续删除仍保留审计 |
| `target_owner_id` | 当时的资源所有者标识，可空 |
| `reason` | 1～500 字符，去除首尾空白 |
| `metadata_json` | 仅允许日期、状态、版本等白名单元数据，禁止正文与模板快照 |
| `created_at` | UTC 操作时间 |

审计行不可通过普通业务 API 修改或删除。日志只记录审计事件 ID、动作和请求 ID，不重复写原因之外的业务数据，更不得写正文。

#### 5.6 `users` 与 `user_settings`

- `users` 增加 `must_change_password BOOLEAN NOT NULL DEFAULT 0`。迁移前已存在的账号均设为 `false`；新建默认管理员为 `true`。
- 管理员重置密码时把目标账号的 `must_change_password` 设为 `true`；用户本人成功修改密码后设为 `false`，同时递增 `token_version` 使旧 Token 失效。
- 重建 `user_settings`，删除 `auto_archive_on_submit`，保留 `timezone`。第二版仍固定 Asia/Shanghai，暂不新增 AI 配置字段。

### 6. 日期级事务与并发设计

#### 6.1 日期行作为写入互斥点

所有会改变某一日期的操作——创建、保存、删除、提交、管理员撤销和日期归档——必须在同一数据库事务内锁定/触碰对应 `daily_report_days` 行并复查 `status=open`。SQLite 没有 `SELECT ... FOR UPDATE`，Repository 使用条件 `UPDATE daily_report_days SET version=version, updated_at=updated_at WHERE id=:day_id AND status='open'` 取得写锁，再读取条目并执行状态转换。

创建首条条目时先 `INSERT ... ON CONFLICT(user_id, work_date) DO NOTHING` 建立日期行，再锁定该行。SQLite 单写者模型、`busy_timeout`、日期唯一约束和短事务共同保证同日操作串行；数据库繁忙继续映射为 `50301`，服务端不做可能重复写入的隐式重试。

#### 6.2 创建条目的幂等规则

1. renderer 在一次用户意图开始时生成 `client_request_id`；网络重试、超时重试和重复响应恢复必须复用该值。
2. Service 获取或创建日期容器并复查未归档。
3. 按 `client_request_id` 查询；若已存在且归属当前用户，则返回既有条目，响应标记 `created=false`。
4. 不存在时读取当前模板，固化模板版本/快照并插入新草稿，响应标记 `created=true`。
5. 极低概率的全局幂等键碰撞若归属其他用户，返回冲突且不泄露对方资源。

不同 `client_request_id` 的连续或并发点击代表不同创建意图，可以生成多篇真实条目；这与请求重试幂等不冲突。

#### 6.3 保存、删除与提交

- 保存：要求所有者、日期 `open`、条目 `draft`、`version` 匹配；模板字段校验允许必填暂空，成功后版本加一。
- 删除：要求相同条件，按条目 `id + day_id + version + draft` 条件删除。删除后若日期容器没有任何条目，Service 在同一事务删除空的 `open` 日期行，月历恢复“未记录”。
- 提交：要求所有者、日期 `open`、条目 `draft`、`version` 匹配；执行完整必填/类型校验，只更新为 `submitted` 并写 `submitted_at`，不得读取个人设置自动归档。
- 任一条件更新失败后回滚并重新读取当前状态，区分 404、日期已归档、状态冲突和版本冲突；不能先更新前端再假定成功。

#### 6.4 管理员撤销提交

管理员列表查询只返回最小元数据。撤销在单事务内完成：

1. 通过专用 Admin Repository 按条目 ID 读取条目和日期元数据，不返回/解析 `content_json` 与 `template_snapshot_json`。
2. 锁定日期行并复查 `open`，验证条目仍为 `submitted` 且版本匹配。
3. 条件更新为 `draft`，清空 `submitted_at`，版本加一；正文、模板快照、创建时间不变。
4. 插入 `admin_audit_events`，保存操作者、原因和白名单元数据。
5. 一次提交。所有者查询条目详情时通过审计表返回最近一次撤销的原因、操作者显示名和时间。

日期归档与管理员撤销争用同一日期写锁：先完成的事务决定结果。若归档先完成，撤销看到 `archived` 并拒绝；若撤销先完成，归档看到草稿并拒绝，绝不会出现正式快照与来源状态不一致。

#### 6.5 日期级归档算法

输入为所有者、`work_date` 和显式 `confirm_archive=true`。事务步骤：

1. 按 `(user_id, work_date)` 获取日期容器。不存在时返回 404；已归档时幂等返回现有正式日报，不重写 `archived_at`。
2. 锁定 `open` 日期行，重新读取当天全部条目。
3. 若有 `draft`，返回冲突并给出 `draft_count`；若没有 `submitted`，返回“没有可归档条目”。
4. 按 `submitted_at ASC, id ASC` 排序全部 `submitted`，解析并校验各自模板快照和内容，生成 `schema_version=2` 正式快照。
5. 以同一 `now` 将全部 `submitted` 条件更新为 `archived`、写 `archived_at`、版本加一；更新行数必须等于步骤 3 的条目数，否则整个事务回滚。
6. 条件更新日期容器为 `archived`，写快照、`source_count`、`archived_by`、`archived_at` 并递增版本；更新行数必须为 1。
7. 提交后返回日期级正式日报。周报、导出和完成率从此只读取该日期行及其正式快照。

任何 JSON 校验、更新行数或数据库操作失败都回滚，不能留下部分 `archived` 条目或半份快照。重复/并发归档最终最多一行 `(user_id, work_date)`，后到请求读取并返回已有结果。

### 7. 首次初始化、认证与用户删除

#### 7.1 双账号初始化

`POST /api/v1/system/bootstrap-admin` 替换为 `POST /api/v1/system/bootstrap`。请求只收首次普通用户的 `username/password/display_name`，服务端固定创建：

- 普通用户：用户输入的账号，`role=user`，`must_change_password=false`；
- 默认管理员：`username=admin`、显示名“系统管理员”、`role=admin`、`must_change_password=true`，密码为同一输入分别哈希后的结果。

普通用户名先做 `strip().casefold()`，等于 `admin` 时拒绝。事务先用当前 `INSERT ... SELECT ... WHERE NOT EXISTS(users)` 形式原子插入普通用户，以 SQLite 写锁作为并发门禁；成功后创建 admin，再分别创建设置、默认模板和模板版本。任一步失败全部回滚；第二个并发请求只能插入 0 行并返回已初始化。两个密码哈希必须分别调用 Argon2id，不能复制哈希字符串，也不能将明文写入模型、日志或审计。

#### 7.2 强制修改默认管理员密码

`GET /auth/me` 增加 `must_change_password`。默认管理员使用初始密码登录后仍获得短期 JWT，但前端路由守卫只能进入 `/change-password`；后端业务依赖 `get_current_business_user` 在认证、启用状态和 `token_version` 校验后检查该标志，除 `/auth/me`、`PUT /auth/password` 和 `/auth/logout` 外统一返回 `40303 PASSWORD_CHANGE_REQUIRED`。

成功修改密码后将 `must_change_password=false`、递增 `token_version` 并要求重新登录。管理员重置任意用户密码时设为 `true`，避免管理员知道的临时密码长期有效；被重置用户同样先进入强制改密页。

#### 7.3 用户安全删除

`DELETE /api/v1/users/{user_id}` 仅 admin 可用，请求必须包含 `confirm_username` 和 1～500 字符 `reason`。Service 在单事务内执行：

1. 禁止删除当前登录账号；禁止删除最后一个有效管理员。
2. `confirm_username` 必须与当前用户名完全一致。
3. 检查目标是否存在日报日期/条目、周报、导出任务或其他业务记录；任一存在即返回 `40910 USER_HAS_BUSINESS_DATA`，提示停用，不做级联。
4. 无业务记录时删除其默认模板版本、模板、个人设置和用户行；先写 `user_deleted` 审计，保留操作者、目标用户名快照和原因，不保留密码信息。
5. 并发检查与删除必须依赖外键 `RESTRICT` 作最终防线；若检查后出现业务数据，删除失败并整体回滚。

用户列表返回 `can_delete` 和不可删除的非敏感原因码，方便界面提前禁用，但服务端删除时仍必须重新检查。普通用户既看不到菜单，也无法直接调用用户管理、管理员撤销或审计接口。

```json
  "current_streak_days": 2,
  "days": []
}
```

当前月分母截至 Asia/Shanghai 今天；历史月为整月；未来月分母为 0、`completion_rate=null`，前端显示 `--`。完成日期只认 `daily_report_days.status=archived`。日报篇数统计工作日期在所选月且状态为 `submitted/archived` 的条目，草稿不计；周报篇数按 `week_start` 所在月。连续天数不受所选月份影响，始终按今天/昨天规则查询最近完成日期。

#### 8.7 新增业务错误码

| code | HTTP | 含义 |
|---:|---:|---|
| 40303 | 403 | 必须先修改临时密码 |
| 40905 | 409 | 日期已经归档，不能继续修改 |
| 40906 | 409 | 日期仍有草稿，不能归档 |
| 40907 | 409 | 日期没有可归档的已提交条目 |
| 40908 | 409 | 创建幂等键与其他资源冲突 |
| 40910 | 409 | 用户已有业务记录，不能物理删除 |

现有 `40401` 所有权隐藏、`40902` 状态不允许、`40904` 版本冲突和 `50301` 数据库繁忙继续复用。API 不返回驱动错误、SQL、密码、Token、正文或其他用户资源信息。

### 9. 周报与 Excel 导出适配

#### 9.1 周报来源与内容快照

周报可用性按七个日期容器计算：无容器为 `none`，`open` 根据条目计数显示草稿/待归档，`archived` 才是可用来源。生成和重生成只读取该周 `daily_report_days.status=archived` 的正式快照，不直接读取来源条目，防止同一天多次进入周报。

周报 `generated_content_json` 和 `source_snapshot_json` 升级为版本化结构：

```json
{
  "schema_version": 2,
  "days": [
    {
      "work_date": "2026-08-07",
      "daily_report_day_id": "01...",
      "source_count": 2,
      "entries": [
        {
          "daily_report_id": "01...",
          "submitted_at": "2026-08-07T09:00:00+00:00",
          "fields": []
        }
      ]
    }
  ],
  "supplement": "",
  "next_week_plan": "",
  "risks": ""
}
```

规则生成保持“按日期、按来源条目展示”的确定性结构；人工编辑仍只修改三块自由文本，重新生成仍需 `confirm_overwrite` 和周报版本。来源跳转从 `/daily/{entry_id}` 改为“我的日报”指定日期，并展示正式快照和来源条目。

未来 AI 生成可在 Weekly Service 之前增加 `generator` 策略接口，例如 `RuleWeeklyGenerator`/`AiWeeklyGenerator`，但本次只实现规则生成器；不增加模型配置表、密钥字段、网络请求或占位 API。

#### 9.2 Excel 导出

导出的选择对象从条目 ID 改为 `daily_report_day_ids`；按日期范围筛选时也只查 `daily_report_days.status=archived`。每个完成日期仍只输出一行正式记录，基础列增加“来源条目数”。

动态列继续按稳定 `field_key` 规划。一个日期的多篇来源中同一 `field_key` 出现多次时，按正式快照顺序收集：单值直接写入，多值在同一单元格按行写为 `[1] 值`、`[2] 值`，保留来源边界；数值只有单值时可保持数值类型，多值统一为文本。未知模板字段不能静默丢弃。`=` 前缀公式注入防护继续适用于每个文本值和聚合后的单元格。

历史已成功的 `export_jobs.request_json` 和生成文件不重写、不重新执行；新任务记录使用 `daily_report_day_ids`。显式选择包含不存在、越权或未归档日期时整体拒绝，返回问题 ID，不静默过滤。

### 10. V1 数据迁移与回滚

新增一份 Alembic 迁移，启动流程仍先 WAL checkpoint、创建时间戳备份，再 `upgrade head`；迁移失败停止 sidecar。迁移必须同时通过空库升级和真实 V1 数据副本升级测试。

#### 10.1 升级步骤

1. 创建 `daily_report_days`、`admin_audit_events` 和所需索引；给 `users` 增加 `must_change_password=false`。
2. 对每个现有 `daily_reports` 行创建一个日期容器，令 `daily_report_days.id=old_daily_report.id`，从而无需改变已有周报来源标识：
   - 旧 `draft/submitted` -> 日期 `open`，不写正式快照；
   - 旧 `archived` -> 日期 `archived`，用这一篇旧日报构造 `schema_version=2`、单来源条目的正式快照，`source_count=1`，归档人取所有者，归档时间沿用旧值。
3. 重建 `daily_reports`：保留原 ID、状态、模板快照、内容、版本和时间；`day_id=old.id`、`client_request_id=old.id`，删除旧的 `user_id/work_date` 列及唯一约束。
4. 重建 `weekly_report_sources`：将 `daily_report_id` 列改为 `daily_report_day_id`，值保持不变，外键改指日期容器。
5. 逐行解析并升级既有周报 JSON：每个旧 `days[]` 包装成一个来源条目的 `entries[]`，旧 `daily_report_id` 同时映射为 `daily_report_day_id` 与该单一 `daily_report_id`；写入 `schema_version=2`。解析失败立即中止迁移并由启动备份恢复，不能跳过坏行。
6. 重建 `user_settings` 删除 `auto_archive_on_submit`，保留用户和时区。
7. 逐项验证行数：日期容器数=迁移前日报数、条目数不变、归档容器数=迁移前归档日报数、周报来源数不变、所有外键检查为零错误，然后提交迁移。

迁移利用 V1“每人每天最多一篇”的事实，因此每个旧条目自然对应一个唯一日期容器。旧草稿/已提交升级后可以在相同日期继续创建更多条目；旧归档数据升级后立即关闭日期，行为与历史语义一致。

#### 10.2 降级限制

第二版允许同日多条目，直接降级到 V1 会造成数据丢失。因此 downgrade 只在以下条件全部满足时执行：每个日期最多一个条目、没有撤销审计依赖、所有周报快照可无损还原为单条目结构。任一日期有多个条目时，迁移必须明确拒绝 downgrade；恢复 V1 应使用升级前自动备份，而不是合并或删除用户数据。

#### 10.3 迁移验证数据集

测试副本至少包含：三态日报、多个用户、不同模板版本、跨年周报、导出任务、已停用账号、闰日和未来日期。升级后验证正文/模板快照逐字节等价、日期和时间不偏移、周报来源可追溯、归档日期不能新建、开放日期可新建第二篇。数据库迁移测试不得使用其他分支或历史实现，只用当前 V1 schema 和测试夹具构造旧库。

### 12. 性能、安全与可观测性

- 月历和统计只查询当前用户与指定月份；Repository 不扫描全表后在 Python 过滤。

- 归档事务只做数据库读取、JSON 组装和写入，不生成 Excel、不做网络请求，保持 SQLite 写锁时间可控。

### 14. 关键设计决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 同日多篇与正式日报建模 | 日期容器 1:n 来源条目 | 同时表达日期关闭、唯一正式结果、来源追溯和并发互斥 |
| 正式结果 | 日期行保存版本化不可变快照 | 周报/导出有稳定来源，不依赖后续模板或查询时临时拼装 |
| 归档并发 | 日期行作为所有日期写操作互斥点 | 让创建、撤销和归档在 SQLite 下得到确定顺序 |
| 创建重试 | renderer 生成 `client_request_id` | 区分真实多次点击与网络重试，避免意外重复 |
| admin 权限 | 专用元数据查询，不开放正文 | 满足撤销能力同时维持最小权限和现有隐私边界 |
| 撤销追溯 | 独立白名单审计表 | 草稿可删除但撤销记录仍需保留，且不污染业务日志 |
| 用户删除 | 无业务物理删除，有业务停用 | 避免级联数据损失并与外键 RESTRICT 一致 |
| 周报/导出来源 | 只读取日期级正式日报 | 每个完成日期只进入一次，杜绝来源条目重复统计 |
| 自动归档 | 删除设置与代码路径 | 同日多篇下提交不等于关闭日期，保留会制造双重语义 |
| AI 扩展 | 仅预留生成策略边界 | 本次不引入外部数据传输、密钥和不可验收的空接口 |

# 企业微信日报反向同步技术方案（第三版增量，CR-20260808-02）

> **方案状态**：`WECOM-02..07` 已实现数据、凭证桥、协议、映射、同步编排/API 与 Electron/Vue 交互，`capabilities.wecom_sync` 已在 WECOM-07 切换为 `true`；真实企业微信测试账号、生产打包与发布级全链路验收仍属于 `WECOM-08`，不得把当前开发分支状态描述为已完成发布验收。

## 1. 设计目标与原则

本方案把“系统日期级正式日报 -> 企业微信日报”设计为一个显式、可预览、可追踪的外部同步流程。首版只同步当前用户自己已经归档的正式日报，不改变本地日报状态，不做自动后台重试。

核心原则如下：

1. **正式快照是唯一同步源**：只读取 `daily_report_days.archive_snapshot_json`，保证同一日期重复预览得到稳定结果。
2. **业务与协议隔离**：FastAPI 负责所有权、映射、幂等和同步状态；企业微信内部协议集中在独立 Client，不散落到 Router、Service 或 Vue。
3. **凭证不落业务库**：Cookie jar 只由 Electron Main 使用 `safeStorage` 加密保存；SQLite 只存不透明 `credential_slot` 和非敏感连接元数据。
4. **不把 Cookie 交给 renderer**：登录窗口、Cookie 读取和凭证解密只在 Electron Main；Vue 只能触发受限 IPC，不能读取 Cookie、文件路径或 Main-only 密钥。
5. **失败保守**：无法证明远端未受理时进入 `uncertain`，不自动重试；模板结构变化时先阻断，不按旧协议猜测提交。
6. **每用户隔离**：连接、模板配置、同步记录均按系统用户所有权过滤；admin 默认无权查看他人企业微信配置、Cookie 或日报正文。

## 2. 当前实现与样例协议分析

### 2.1 现有日报数据链路

当前日报已经采用“日期容器 1:n 来源条目”：

- `daily_report_days`：`(user_id, work_date)` 唯一；`status=open/archived`；归档时保存不可变 `archive_snapshot_json`。
- `daily_reports`：同日多篇来源条目，保存 `template_snapshot_json` 和 `content_json`；日期归档后条目进入 `archived`。
- `DailyReportDayService.build_day_archive_snapshot()`：按 `submitted_at ASC, id ASC` 构造 `schema_version=2` 的正式快照，每个来源包含 `daily_report_id`、`template_version_id`、`template_snapshot` 和 `content`。

企业微信同步不能从草稿、开放日期或当前模板重新拼数据；必须复用该正式快照，保持与周报、导出的正式来源口径一致。

### 2.2 `wx-ribao.py` 的登录方式

参考脚本使用 Python Playwright 启动可见 Chromium，打开企业微信文档表单地址，等待用户完成网页登录后读取浏览器上下文 Cookie。该方式可以覆盖扫码、设备确认等交互，但脚本以固定等待时间判断完成，生产实现应改为“目标页面/接口校验成功”而非仅等待秒数。

生产实现不直接运行或导入该脚本：桌面应用已经内置 Electron Chromium，继续引入 Python Playwright 会增加第二套浏览器运行时、打包体积和进程生命周期。方案复用脚本验证出的登录与协议知识，在 Electron Main 中实现受控登录窗口。

### 2.3 Cookie 管理分析

脚本当前从完整 Cookie 集合中挑选 `TOK`、`traceid`、`hashkey`、`tdoc_uid`、`wedoc_openid`、`wedoc_sid`、`wedoc_sids`、`wedoc_skey`、`wedoc_ticket` 等名称，并写入明文文件；真实提交样例还出现 `TrustID`、`utype` 等补充 Cookie。这证明固定白名单容易随页面或风控变化而遗漏。

正式实现保存完整的结构化 Cookie jar，至少保留 `name/value/domain/path/secure/httpOnly/sameSite/expirationDate`。发送请求时再按目标 URL 的域、路径、安全属性和过期时间筛选，不把全部 Cookie 无条件拼给所有主机。脚本中的固定标记值和明文 `cookies.txt` 机制不得进入生产代码。

### 2.4 已验证的企业微信内部接口

#### 获取模板与组合信息（仅连接时使用）

- 方法：`POST`
- 地址：`https://doc.weixin.qq.com/journal/get_template_combine_info?_prefetch=1`
- JSON 语义：`form_id`、`fetch_journal_list=true`、`is_pre_create=false`、`is_answer_from_share=false`、`is_answer_from_workplace=false`、`fetch_submission_type=1`、`is_only_view=true`。
- 成功判断：`head.ret == 0`。
- 关注返回：`body.entrys`、`body.template_id` 及表单题目结构。
- 用途：仅 `WeComConnectionService.validate_connection`（首次连接）调用，用来发现并保存 `template_id`——这是提交时 `wwjournal_data.entry.templateid` 必需的字段，而 `formcol/detail` 的响应不包含它，没有其他已验证接口能提供。执行同步阶段不再调用这个接口。

#### 获取表单结构与提交历史（执行同步时使用）

- 方法：`GET`
- 地址：`https://doc.weixin.qq.com/formcol/detail?_t={毫秒时间戳}&f=json&lang=zh&form_id={form_id}`
- 与其余三个接口不同：不需要 `sid`/`wedoc_xsrf` 查询参数，仅依赖 Cookie 鉴权。
- 成功判断：`head.ret == 0`。
- 关注返回：
  - `body.stat_info.question_infos[]`（`question_id`/`title`/`type`/`must_reply`）：与已保存的 `question_mapping_json` 重新比对结构指纹，字段语义等价于旧接口的 `body.form.question.items[]`，但没有 `ext`（因此无法提供 `qdata_sub_type`，结构指纹不再纳入该字段，见 §7.1 之后的修订说明）。
  - `body.stat_info.fork_items[]`（`form_id`/`ctime`/`status`）：本人这份周期性日报表单的**实例**列表（哪些日期存在一个 fork），不是"哪些日期已提交内容"——两者不等价，且没有字段能区分。仍会抓取并建模（`WeComFormDetailForkItem`），但不再用于阻断提交，详见 §10.2 第二次修订。
  - `body.stat_info.creater_vid`/`creater_name`：连接时依赖的"猜测归属"逻辑仍保留在连接流程，这里未使用。
- 取代原 `wework/journal/get_journal_list` 查重接口的结构复核职责，原因见本节开头的修订说明；查重职责本身已于 §10.2 第二次修订整体移除。

#### 提交日报

- 方法：`POST`
- 地址：`https://doc.weixin.qq.com/formcol/answer_page?sid={wedoc_sid}&wedoc_xsrf=1`
- 编码：`multipart/form-data`，边界由 HTTP 客户端生成，不能复用原始样例中的固定边界。
- 表单部分：
  - `form_id`
  - `form_reply`：按目标题目 ID 组织的日期、今日工作内容、明日工作计划回复 JSON。**真实抓包确认两种题目类型的回复形状不同**：`reply_type=24`（"富文本"，本集成目前观察到的今日工作/明日计划题目类型）必须使用 `{"question_id":…,"rich_text_reply":{"text_reply":"<div>…</div>","plain_text_reply":"…"}}`（`text_reply` 是 HTML 转义并用 `<div>`/`<br>` 包裹的版本，`plain_text_reply` 是原始文本）；`reply_type=11`（日期）沿用 `{"question_id":…,"text_reply":…}`。用哪种形状由 `formcol/detail` 当次返回的题目 `type` 决定，不依赖本地保存的 `question_mapping_json`（本地只保存归一化后的 `text/date/select` 大类，不携带这层线格式细节）。
  - `type=8`
  - `check_setting={"can_anonymous":2}`
  - `use_anonymous=false`
  - `submit_again=true`
  - `wwjournal_data`：包含 `templateid`（取自连接时保存在 `wecom_sync_profiles.template_id` 的值，不从 `formcol/detail` 重新获取）、`doc_info`、`mngreporter`、`reporter` 等日报上下文
  - `isSendToRoom=false`
  - `f=json`
- 成功判断：HTTP 成功之外还必须满足 `head.ret == 0`。
- 成功返回：`body.form` 给出当前表单结构；`body.answer_replys` 给出新提交的 `answer_id`、`reply_id`、`journaluuid`、`user_vid` 等；`body.repeat_before_replys` 可能包含历史提交。

协议中的数值型或字符串型标识统一在 Client 边界规范化为字符串。任何 HTTP 200 但业务码非零、内容类型异常或必需节点缺失都视为协议/业务失败，不能记录为成功。

## 3. 整体架构

```text
Vue 日报/设置页面
    │ 公开 REST：预览、创建同步记录、查状态、保存映射
    ▼
FastAPI WeCom API
    │
    ├─ WeComConnectionService
    ├─ WeComDailyMapper
    └─ WeComSyncService
          │
          ├─ Repository -> SQLite
          │     ├─ wecom_user_bindings
          │     ├─ wecom_sync_profiles
          │     └─ wecom_daily_sync_records
          │
          └─ WeComInternalClient -> doc.weixin.qq.com 内部接口
                    ▲
                    │ Cookie jar 仅在单次 Main-only 回环请求中传入
Electron Main
    ├─ WeComAuthWindowController 受控网页登录
    ├─ WeComCredentialStore -> safeStorage 加密文件
    └─ WeComBridgeClient -> Main-only FastAPI 内部端点
```

### 3.1 信任边界

现有 `X-Runtime-Secret` 会经受限 preload 进入 renderer 的 API 客户端，因此不能用它保护携带 Cookie 的内部端点。本增量新增随机 `main_bridge_secret`：

- Electron Main 每次启动生成，只在内存持有。
- 通过 sidecar 子进程环境传给 FastAPI，不进入 Vite 变量、preload、renderer、日志或持久化文件。
- `/api/v1/internal/wecom/**` 同时校验 `X-Main-Bridge-Secret` 和当前用户 JWT；只有 Main 能解密 JWT/Cookie 并完成调用。
- 公开 REST 不接受 Cookie、Cookie header、凭证文件路径或 `credential_slot` 写入。

### 3.2 外部请求执行边界

企业微信 HTTP Client 放在 FastAPI，是因为字段预检、幂等状态和结果落库属于业务事务；Electron Main 只承担浏览器登录、系统加密和把一次性解密出的 Cookie jar送到 Main-only 端点。Cookie 只在本机回环请求内短暂存在，FastAPI Client 使用后立即释放，不写数据库或磁盘。

外部 HTTP 调用期间不能持有 SQLite 写事务：

1. 短事务校验所有权、正式日报、配置和幂等记录，条件更新为 `syncing` 后提交。
2. 在事务外完成模板复核、重复检查和提交。
3. 用新的短事务按 `record_id + attempt_token + status=syncing` 条件写入最终状态，防止迟到响应覆盖新尝试。

## 5. 连接与同步时序

### 5.1 连接企业微信

1. renderer 调用 `runtimeBridge.wecom.connect()`。
2. Main 创建隔离登录窗口，用户自行完成登录、验证码或设备确认。
3. Main 读取完整 Cookie jar，在内存生成随机 `credential_slot`，用 `safeStorage` 加密保存。
4. Main 调用内部连接校验端点，携带当前 JWT、`main_bridge_secret`、Cookie jar、`credential_slot` 和目标表单标识。
5. FastAPI Client 调模板组合接口，验证账号/表单/三个目标题目并计算结构指纹；Service 原子保存绑定和初始配置。
6. 任一步失败时删除本次新建的凭证槽；成功后 renderer 只收到非敏感账号、模板和映射摘要。

### 5.2 预览

1. renderer 调 `POST /api/v1/wecom/previews`，传 `daily_report_day_id`。
2. Service 校验 owner、`status=archived`、连接和配置。
3. Mapper 解析正式快照，输出日期、今日工作内容、明日工作计划、来源数量、字符数、未映射字段列表。
4. 预览正文只返回给所有者当前请求，不持久化、不写日志。

### 5.3 执行同步

1. renderer 调公开 REST 创建或取得 `pending` 同步记录；成功记录直接返回，不再执行。
2. renderer 调受限 IPC；Main 先通过双鉴权且隐藏 OpenAPI 的槽位查询端点按当前 JWT 取得本人 `credential_slot` + `connection_status`，只在状态为 `connected` 时解密对应 Cookie。该查询使应用重启后仍能恢复持久化登录态，也可在断开响应丢失时读取真实状态完成对账，且槽位不进入 preload/renderer。
3. Main 调内部执行端点；Service 条件更新为 `syncing`，生成 `attempt_token` 并提交本地短事务。
4. Client 调 `formcol/detail` 重新获取模板结构并比对指纹（§2.4 修订）；不再做远端重复检查（§10.2 第二次修订：`fork_items` 无法可靠区分空壳实例与已提交内容，检查本身在每次尝试上都会误判）。
5. Mapper 生成规范化载荷，Client 提交 multipart。
6. Service 按结果写入 `succeeded` 或分类失败，远端 ID 只保存必要字段；Main 清除内存中的 Cookie 副本。

## 6. 数据库设计

### 6.1 是否新增 Cookie 表

**不新增。** Cookie 是可直接代表用户会话的高敏感凭证，SQLite 整库未加密且可由管理员备份导出，不适合保存 Cookie 值。数据库只保存随机 `credential_slot`；实际 Cookie jar 位于 Electron `userData` 下的独立加密文件，由 `safeStorage` 保护，并明确排除手动数据库备份。

### 6.2 `wecom_user_bindings`

| 字段 | 约束 | 说明 |
|---|---|---|
| `id` | ULID PK | 绑定标识 |
| `user_id` | FK users，UNIQUE，RESTRICT | 每个系统用户一个绑定 |
| `credential_slot` | UNIQUE，非空 | Main 凭证存储的不透明随机键，不是路径 |
| `wecom_vid` | 非空 | 当前企业微信用户的远端标识 |
| `display_name` | 非空 | 仅用于本人确认连接账号 |
| `corp_id` | 可空 | 能可靠发现时保存 |
| `status` | CHECK | `connected/expired/disconnected` |
| `last_validated_at` | 可空 | 最近成功校验 |
| `last_auth_error_at` | 可空 | 最近认证失效 |
| `version` | 正整数 | 乐观锁 |
| `created_at/updated_at` | UTC | 审计时间 |

该表不保存 Cookie 名称、值、header 或本地文件绝对路径。

### 6.3 `wecom_sync_profiles`

首版每个 `user_id` 唯一一行，代表当前启用目标：

| 字段 | 说明 |
|---|---|
| `id/user_id` | ULID、owner FK/UNIQUE |
| `form_id/template_id/journal_uuid` | 远端表单、模板和可选日报上下文标识 |
| `destination_fingerprint` | 对 `form_id + template_id` 的规范化 SHA-256，用于目标幂等 |
| `question_mapping_json` | 日期/今日/明日的题目 ID、reply type、子类型及提交顺序，`schema_version=1` |
| `recipient_config_json` | `mngreporter/reporter` 的 vid 列表及版本 |
| `field_mapping_json` | 稳定 `field_key -> today_work/tomorrow_plan/ignore` 规则及未映射策略 |
| `schema_fingerprint` | 目标三题目 `question_id + reply_type` 的规范化 SHA-256（2026-08-09 起不再纳入 `qdata_sub_type`：执行同步阶段改用的 `formcol/detail` 不提供该字段，见 §2.4 修订） |
| `version/is_active` | 配置版本和启用状态 |
| `created_at/updated_at` | UTC |

这张表即“企业微信模板配置表”，无需再建一张只复制相同配置的表。配置更新递增 `version`；同步记录保存当次 `profile_version`，便于解释历史结果。

### 6.4 `wecom_daily_sync_records`

| 字段 | 说明 |
|---|---|
| `id` | ULID PK |
| `user_id` | owner FK |
| `daily_report_day_id` | 正式日报日期 FK |
| `profile_id/profile_version` | 本次目标配置及版本 |
| `destination_fingerprint` | 目标表单/模板指纹 |
| `payload_fingerprint` | 正式快照 + 映射结果规范化 SHA-256，不保存正文副本 |
| `status` | `pending/syncing/succeeded/failed/auth_required/schema_changed/duplicate_detected/uncertain` |
| `attempt_count/attempt_token` | 尝试次数和本次条件完成令牌 |
| `remote_answer_id/remote_reply_id/remote_journal_uuid` | 成功或对账所需的非敏感远端 ID，可空 |
| `last_error_kind/last_error_message` | 白名单错误类型和脱敏短消息 |
| `last_attempt_at/succeeded_at/created_at/updated_at` | UTC |

唯一约束为 `(daily_report_day_id, destination_fingerprint)`：同一正式日报向同一目标只能有一条状态记录；切换到不同表单/模板后可以创建新的目标记录。索引至少覆盖 `(user_id, status, updated_at)` 和 `daily_report_day_id`。

同步记录不保存提交请求体或响应原文。`succeeded` 是终态；迟到响应必须带匹配 `attempt_token` 才能写入。

### 6.5 用户删除与备份

- 无同步历史的用户：User Service 在同一事务显式删除 profile、binding 后再删除用户；提交事务成功后由 Main 删除对应凭证槽。若凭证删除失败，记录脱敏本地清理告警，不恢复已删除账号。
- 有同步记录的用户：按既有“有业务记录不物理删除”规则返回 `40910`，建议停用账号。
- 手动整库备份包含三张非敏感元数据表，但不包含 `safeStorage` 凭证文件；备份说明需明确企业微信登录态不会随数据库迁移到另一台设备。

## 7. 字段映射设计

### 7.1 映射输入

Mapper 逐个读取正式快照 `entries[]`。每个字段由同一 entry 内的 `template_snapshot[field_key]` 与 `content[field_key]` 配对；不依赖数据库中的当前模板版本。

默认建议规则：

| 本地字段 | 目标 | 规则 |
|---|---|---|
| `daily_report_days.work_date` | 日期 | 强制映射，不能关闭 |
| `core_type=today_work` | 今日工作内容 | 默认映射；空值跳过 |
| `field_type=PROJECT_LIST` | 今日工作内容 | 默认映射为项目分段 |
| `core_type=tomorrow_plan` | 明日工作计划 | 默认映射；目标必填时不能为空 |
| 责任人类自定义字段 | 今日工作内容 | 由用户按 `field_key` 确认后，以“责任人:值”附加（半角冒号，见 §7.2 说明） |
| 其他非空字段 | 未映射 | 预检阻止并要求选择今日/明日/忽略 |

标签匹配只用于首次配置时给出候选，不得把“名称包含计划”作为运行时规则。用户确认后保存稳定 `field_key`。

### 7.2 格式化

项目列表单项（示例文本中的冒号用半角 `:`，不是本节其余中文叙述常用的全角“：”——`WECOM-05` 实现时发现仓库全部 Python 源码的 Ruff 规则 `RUF001`/`RUF002`/`RUF003` 禁止全角中文标点且无例外，为了让示例文本和真实产出的字符串保持一致，这里改为半角）：

```text
项目:项目名称
工作内容:本项工作内容
完成状态:进行中
```

“责任人”不是 `PROJECT_LIST` 每一项自带的属性（`ProjectListEntry` 只有 `project`/`content`/`status` 三个字段），而是一个独立的自定义字段，按下面“普通自定义字段”规则映射到今日工作内容，格式化后追加在同一来源全部 `PROJECT_LIST` 分段之后。

多项目之间空一行。多来源正式日报按快照顺序输出；只有一个来源时不添加冗余序号，多个来源时使用“日报 1”“日报 2”分段。普通自定义字段用“字段标签:格式化值”（半角冒号）；空值不输出，字段顺序沿用模板快照 `sort_order`。

`PROJECT_LIST` 的状态固定映射：

| 本地值 | 企业微信文本 |
|---|---|
| `TODO` | 待开始 |
| `DOING` | 进行中 |
| `DONE` | 已完成 |

目标模板只有三题，因此“项目、工作内容、完成状态、责任人”都被编排进“今日工作内容”，不虚构企业微信中不存在的独立题目。

### 7.3 预检

发请求前必须验证：

- 正式快照 schema 合法，来源与字段顺序可确定。
- 三个目标题目仍存在，reply type/subtype 与配置一致。
- 所有非空字段均已映射或显式忽略。
- 日期、今日、明日满足目标必填约束。
- 文本未超过远端元数据限制；不静默截断。
- recipient 配置非空且结构合法。

## 8. 企业微信 Client 设计

`WeComInternalClient` 使用异步 `httpx.AsyncClient`，显式设置连接、写入、读取和连接池超时；禁用无边界重定向，只允许 HTTPS 和批准的企业微信文档主机。生产依赖中不新增 Python Playwright。

Client 对外只暴露稳定方法：

- `get_template_info(cookie_jar, form_id) -> WeComTemplateInfo`
- `list_journals(cookie_jar, template_id, cursor) -> WeComJournalPage`
- `submit_daily(cookie_jar, payload) -> WeComSubmissionResult`

每次请求：

1. 从 Cookie jar 按 URL 选择未过期 Cookie，提取当前请求所需 `wedoc_sid`；缺失则返回认证失效。
2. 请求前不记录 header/body。企业微信诊断写入独立轮转文件 `wecom.log`：默认脱敏时只记录 method、主机、路径模板、耗时和分类结果；设置 `WEEKLY_REPORT_WECOM_LOG_REDACT=false` 并重启应用后，可额外记录 HTTP 状态、固定异常类型/文案、企业微信业务码、不含题目标题/标识的结构计数，以及经过标识符正则、深度/数量/长度上限约束的协议字段路径和纯数字题型枚举。字段路径只遍历 JSON key，不记录任何 value。无论开关取值如何，Cookie、Authorization/JWT、运行时密钥、请求/响应 header、请求/响应正文、表单/模板/成员标识及日报正文均不得进入日志。日志位于 `log_dir/wecom.log`，单文件上限 2 MiB，保留 5 个轮转备份。
3. 校验 HTTP 状态、`Content-Type`、JSON 深度/大小、业务码和必需字段。
4. 把远端标识规范化为字符串，把未知额外字段忽略在协议 DTO 边界。
5. 用异常类型区分 `WeComAuthExpired`、`WeComSchemaChanged`、`WeComBusinessRejected`、`WeComProtocolChanged`、`WeComTransportFailed`、`WeComOutcomeUncertain`。

## 9. API 与 IPC 契约

### 9.1 公开 REST

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/wecom/connection` | 本人连接状态和非敏感账号摘要 |
| GET | `/api/v1/wecom/profile` | 本人当前映射配置 |
| PUT | `/api/v1/wecom/profile` | 版本化更新字段/接收人映射 |
| POST | `/api/v1/wecom/previews` | 生成指定正式日报的临时转换预览 |
| POST | `/api/v1/daily-report-days/{work_date}/wecom-syncs` | 幂等创建/取得目标同步记录 |
| GET | `/api/v1/wecom/sync-records` | 本人同步历史，支持状态/日期筛选 |
| GET | `/api/v1/wecom/sync-records/{record_id}` | 本人同步详情，不返回请求/响应原文 |
| POST | `/api/v1/wecom/sync-records/{record_id}/retry` | 只为允许重试的状态重新置为待执行 |

所有公开接口同时校验 JWT、强制改密状态和现有 runtime secret。所有权不匹配统一返回 `40401`。

### 9.2 Main-only REST

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/internal/wecom/connections/validate` | 校验内存 Cookie、发现模板并提交绑定 |
| GET | `/api/v1/internal/wecom/connections/credential-slot` | 只向 Electron Main 返回当前 JWT 所有者的不透明凭证槽位与连接状态；无绑定时两者均为 `null` |
| POST | `/api/v1/internal/wecom/sync-records/{record_id}/execute` | 使用内存 Cookie 执行已预留同步 |
| POST | `/api/v1/internal/wecom/connections/disconnect` | 标记断开；凭证文件由 Main 先删除 |

内部接口必须同时校验当前用户 JWT 与 `X-Main-Bridge-Secret`，且只接受结构化 Cookie jar，不接受原始 `Cookie` header 字符串或任意目标 URL。

### 9.3 IPC

`runtimeBridge.wecom` 只允许：

- `connect()`：打开固定企业微信登录流程。
- `disconnect()`：删除当前用户凭证并通知后端。
- `executeSync(recordId)`：`recordId` 必须符合 ULID 格式；目标 URL 和请求体由后端记录决定。

所有 IPC 校验 `event.senderFrame` 是当前业务窗口的主 frame。禁止提供“读取 Cookie”“发送任意 HTTP”“打开任意 URL”或“读取凭证文件”接口。

### 9.4 拟新增错误码

| code | HTTP | 含义 |
|---:|---:|---|
| 40911 | 409 | 企业微信未连接或登录已失效 |
| 40912 | 409 | 企业微信模板结构已变化 |
| 40913 | 409 | 该正式日报已成功同步 |
| 40914 | 409 | 上次同步结果不确定，禁止直接重试 |
| 40915 | 409 | 检测到可能的企业微信重复日报 |
| 50201 | 502 | 企业微信内部协议不符合已知契约 |
| 50302 | 503 | 企业微信暂时不可用且可确认未受理 |

日报未归档继续复用现有状态不允许错误，不新建同义错误码。响应只给出用户可行动建议和本地 `record_id`，不透传企业微信原始响应。

## 10. 幂等、并发与重复同步

### 10.1 本地幂等

- 数据库唯一约束 `(daily_report_day_id, destination_fingerprint)` 是最终防线。
- 创建同步记录用“查询既有 + 捕获唯一约束”的并发安全模式；两个点击最多创建一条记录。
- `succeeded` 直接返回既有记录；`syncing` 返回处理中；其他状态按状态机决定是否允许动作。
- `pending/failed -> syncing` 使用条件更新并设置新 `attempt_token`；只有持有该 token 的响应能完成本次尝试。

### 10.2 远端重复检查

> 2026-08-09 第一次修订：原方案在提交前调用日报列表接口（`template_id + user_vid + work_date` 查候选，并能用本地已保存远端 ID 把唯一候选对账为 `succeeded`）。该接口对真实账号持续失败（§2.4 修订），改为提交前调用 `formcol/detail`，用其 `body.stat_info.fork_items` 按 `ctime` 换算日期比对 `work_date` 做重复检查。
>
> 2026-08-09 第二次修订（同日）：真实使用后发现上述 `fork_items` 检查**在每一次同步尝试上都会误判为重复**，即便企业微信里确实不存在当天日报。原因是 `fork_items` 列出的是"这个周期性表单存在哪些日期的实例（fork）"，不是"哪些日期已经真正提交过内容"；`fork_items` 本身没有任何字段能区分"空壳实例"和"已填写提交"。更进一步，`get_form_detail()`（即调用本身）看起来会让"今天"这个 fork 的存在性成立——也就是说，只要调用一次结构复核，检查就会把当天判定为重复，与是否真的提交过无关。这不是"保守但偶尔误判"，而是**结构性 100% 误判**，因此彻底移除了这一层查重：`_perform_remote_sync()` 不再基于 `fork_items` 做任何阻断，拿到结构和指纹校验通过后直接提交，信任 `submit_again=true`（与用户提供的真实成功抓包完全一致，那份抓包本身也不含任何查重调用）。
>
> `fork_items` 仍然会被 `get_form_detail()` 抓取并建模（`WeComFormDetailForkItem`），只是不再被用来阻断提交——保留是因为这是目前唯一已验证、可能在未来找到更可靠判据后重新启用查重的数据来源；`duplicate_detected` 状态本身、其错误码 `40915` 和状态机允许的转换均保留在系统中（不会被任何当前代码路径触发，属于诚实记录的能力缺口，不是运行时可达的死代码风险）。

`formcol/detail` 响应数量（`fork_items`/`question_infos`）仍必须有最大项数限制，避免异常响应导致无限扫描——这一保护与是否做重复检查无关，继续保留。

### 10.3 结果不确定

连接/写入超时、进程中断或收到无法判断是否受理的非契约响应时进入 `uncertain`。

> 2026-08-09 修订：原"下次执行远端对账、找到唯一匹配并取得远端 ID 可转 `succeeded`"依赖的正是 §10.2 已移除的查重机制——`fork_items` 没有可交叉验证的远端 ID，无法安全地自动把 `uncertain` 转回 `succeeded`，§10.2 第二次修订后这层机制干脆整体不存在了。当前代码库里也没有任何调用点会对 `uncertain` 记录触发 `execute()`（`retry()` 显式拒绝，见 `WeComSyncService` 相关代码注释），因此这不是行为倒退，只是把一个原本理论上存在、实际从未被触发过的路径诚实地记录为"暂不支持"：

- 仍无法判断：保持 `uncertain`。
- 未来如果需要恢复"自动对账"/"查重"能力，需要先找到一个能可靠交叉验证"这条记录是不是我自己那次提交、且真的已提交内容"的远端字段（`journalid`/`answer_id` 等，且能区分空壳与已填写），而不是仅凭日期或实例存在性匹配。

启动恢复时，超过合理租约仍为 `syncing` 的记录转 `uncertain`，绝不直接转 `failed`。

## 11. 异常处理

| 场景 | 判定 | 状态与动作 |
|---|---|---|
| Cookie 过期/缺少关键会话 | 登录页重定向、认证业务码、`wedoc_sid` 缺失 | `auth_required`，binding 置 `expired`，引导重新登录 |
| 模板题目 ID/类型/必填变化 | 当前结构指纹与 profile 不一致 | `schema_changed`，保存差异摘要，不提交 |
| 明确业务拒绝 | 业务码非零且能证明未受理 | `failed`，保存白名单 error kind，可人工重试 |
| 连接建立前失败 | DNS/TLS/connect timeout，尚未发送 body | `failed` 或可重试临时失败 |
| 写入/读取超时 | 请求可能已被受理 | `uncertain`，先对账 |
| HTTP 200 但 JSON/节点变化 | 契约校验失败 | 若已发送提交则 `uncertain`，只读接口则 `schema_changed`/协议错误 |
| 本地重复点击 | 唯一约束或现有状态命中 | 返回既有记录，不重复外部调用 |
| SQLite 繁忙 | 本地短事务失败 | 复用 `50301`；外部调用尚未发生时可重试 |

错误消息使用固定中文文案；`last_error_message` 最大长度受限并去除远端原文、URL 查询、标识集合和正文。

## 12. 安全与合规设计

- 用户提供的 `http_raw_request.txt`、`http_raw_response.txt` 视为敏感资料，第一实施任务必须加入精确忽略规则并生成全合成、无真实账号/正文/Cookie 的测试 fixture。
- 不在 Git、日志、Sentry 类遥测、测试快照、数据库、备份或错误响应中保存 Cookie、Cookie 名值对、Authorization/JWT、运行时密钥、表单/模板/成员标识、完整日报正文或完整企业微信响应。`WEEKLY_REPORT_WECOM_LOG_REDACT=false` 只放开白名单诊断元数据（包括有界且只含 key 的协议字段路径和纯数字题型枚举），不关闭上述强制保护。
- `safeStorage` 不可用时企业微信连接功能明确不可用，不允许降级为明文。
- Cookie 文件采用随机槽位、原子替换和仅当前用户可读的目录；不允许用远端 ID 或用户名直接拼文件路径。
- 登录窗口限制导航主机、拒绝 `window.open` 和下载，禁止加载本地文件和任意扩展；不自动填写验证码，不绕过企业安全策略。
- HTTP Client 只允许固定 HTTPS 主机，禁止调用请求体或远端响应指定的 URL，防止 SSRF。
- `main_bridge_secret` 与 runtime secret 分离；二者均不记录、不持久化，Main-only 端点默认不出现在公开 OpenAPI。
- 由于使用非官方内部接口，发布说明必须明确兼容性风险，并在使用前确认组织制度和企业微信相关条款允许该方式。

## 13. 测试策略

### 13.1 后端

- 模型/迁移：空库升级、现有 V2 数据库升级、外键、唯一目标、状态 CHECK、downgrade 数据提示。
- Mapper：三核心字段、动态字段、多个模板版本、`PROJECT_LIST`、多来源顺序、空值、日期、数字/多选、未映射、超长、载荷哈希稳定。

- API：公开/内部双鉴权、强制改密、404 所有权隐藏、响应脱敏、内部端点不进入公开 OpenAPI。

### 13.2 Electron/Vue

- Credential Store：`safeStorage` 成功、不可用、损坏密文、原子写入失败、槽位校验、断开删除；断言无明文回退。
- Auth Window：安全 webPreferences、临时 partition、导航/新窗口/下载限制、用户取消、登录成功、清理。
- IPC：受信任 frame、ULID 校验、无任意 URL/读取 Cookie 能力、Main-only 密钥不出现在 preload/renderer 构建产物。
- UI：连接/失效/模板变化、映射编辑、预览、成功/重复/不确定状态、按钮禁用原因。
- E2E：受控测试账号完成连接 -> 归档日期 -> 预览 -> 同步 -> 重复点击不重发；失效 Cookie、模板变化和请求超时三条失败链路。

真实企业微信冒烟只能使用专用测试账号和非敏感测试日报；自动化日志不得保存页面内容或网络 header。内部接口无法稳定 mock 出全部风控行为，因此发布前真实冒烟是必要但不替代自动化测试。

|---|---|---|
| 生产登录实现 | Electron 隔离 BrowserWindow，不打包 Python Playwright | 复用桌面 Chromium，减少第二浏览器和进程；保留人工登录/验证码 |
| Cookie 存储 | Electron `safeStorage` 加密文件，SQLite 只存槽位 | 避免数据库备份泄露会话凭证，renderer 不接触 Cookie |
| 外部 Client 所在层 | FastAPI `integrations/wecom` | 业务预检、幂等和结果状态集中；Electron 只负责凭证能力 |
| 内部鉴权 | 新增 Main-only 随机 secret + JWT | 现有 runtime secret 对 renderer 可见，不能保护 Cookie 端点 |
| 同步源 | 日期级归档正式快照 | 与周报/导出一致，内容不可变、顺序稳定 |
| 触发方式 | 用户手动、先预览 | 非官方接口风险高，避免归档事务中做网络请求 |
| 本地幂等键 | 日期正式日报 + 目标指纹 | 同一目标不重复，不同目标仍可显式同步 |
| 超时语义 | 可能已发送则 `uncertain` | 防止自动重试产生重复企业微信日报 |
| 模板变化 | 结构指纹不一致即阻断 | 不以题目标题猜测或向旧题目 ID 盲发 |
| 原始协议样例 | 只作本地参考，测试使用全合成 fixture | 防止真实 Cookie、标识和日报正文进入版本库 |

实施过程中若要改为自动同步、将 Cookie 存入 SQLite、让 renderer 读取 Cookie、跳过模板指纹、对 `uncertain` 自动重试、允许 admin 同步他人日报或直接在 Electron 承载业务状态机，均属于安全/架构变更，必须先回到方案评审。
