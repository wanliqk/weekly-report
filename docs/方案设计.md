# 个人日报周报管理系统技术方案（第一版）

## 1. 技术方案概述

系统采用“Electron 桌面客户端 + 本地 FastAPI 业务服务 + SQLite 数据库”的单机多用户架构，首期面向 Windows 10/11 x64。Electron 渲染进程使用 Vite、Vue 3 和 TypeScript 构建界面；Electron 主进程使用 NestJS standalone application context 组织桌面生命周期、本地配置、凭证保存、FastAPI 子进程和受控 IPC；FastAPI 是唯一业务后端，负责认证授权、日报、模板、周报、导出等业务，并作为 SQLite 的唯一写入者。

NestJS 不监听业务 HTTP 端口、不访问 SQLite，也不重复实现 FastAPI 业务逻辑。该安排是对指定技术栈的职责澄清：Vite 是构建工具，需搭配 Vue 3 作为 UI 框架；NestJS 是 Node.js 应用框架，放在 Electron 主进程作为应用容器，而不是第二套后端。

首期按本地桌面应用设计，但 API、数据所有权和用户角色仍保持多用户模型，为将来把 FastAPI 部署为远程服务保留空间。

## 2. 已确认需求与设计基线

- 运行形态：Electron 桌面客户端，首期支持 Windows 10/11 x64。
- 身份认证：用户名、密码登录；JWT 有效期 24 小时；密码修改后已有令牌全部失效。
- 用户角色：`admin` 和 `user`；管理员负责用户管理，普通用户只访问自己的业务数据。
- 日报唯一性：同一用户、同一工作日期最多一份日报，不因草稿、提交或归档状态变化而改变。
- 日报状态：`draft → submitted → archived`；支持个人设置“提交后自动归档”。
- 日报日期：允许补写历史或未来日期；日期已存在日报时进入现有记录，不新建重复记录。
- 归档策略：已归档日报只读，第一版不提供撤回归档。
- 模板策略：两个默认核心字段始终保留，可修改显示名称、说明、顺序和必填属性，但不可删除或停用；模板变更只影响以后创建的日报。
- 周报周期：`Asia/Shanghai` 时区，周一至周日为一个自然周。
- 周报来源：只汇总指定周内已归档日报；草稿或已提交未归档日报仅提示，不进入汇总。
- 周报策略：每个用户每个自然周最多一份周报；允许人工编辑；重新生成必须显式确认，并保留重新生成前的当前内容版本。
- Excel：每份日报一行，动态字段取所选日报字段并集生成列；仅导出已归档日报。
- 企业微信：本期只显示占位入口和能力状态，不连接、不授权、不发送任何外部请求。

| 密码哈希 | Argon2（通过 `pwdlib`） | 不保存明文或可逆密码，采用现代密码哈希算法 |

| 后端测试 | pytest + FastAPI TestClient/httpx | 覆盖服务、权限、状态机和 API 集成测试 |
| 前端测试 | Vitest + Vue Test Utils | 覆盖组件、状态和前端业务逻辑 |

```text

│                                               │

│                 │                             │

│                 │ typed IPC                   │

│                 │                             │
│  Main：NestJS standalone context              │
│  ├─ AuthSession（令牌安全保存）                 │
│  ├─ ApiClient（固定基址和接口白名单）           │
│  ├─ BackendProcess（启动/停止/健康检查）        │
│  ├─ Export（保存对话框和文件写入）              │
│  └─ Window/Config/Logging                      │
└─────────────────┬─────────────────────────────┘
                  │ HTTP 127.0.0.1 + JWT
┌─────────────────▼─────────────────────────────┐
│ FastAPI                                         │
│ API → Service → Repository → SQLAlchemy         │
│ Auth / Users / Settings / Templates / Dailies   │
│ Weeklies / Export / Sync Capability             │
└─────────────────┬─────────────────────────────┘
                  │ 单进程、事务写入
             ┌────▼─────┐
             │ SQLite   │
             └──────────┘
```

### 4.1 通信边界

1. 渲染进程不得启用 Node.js 集成，不直接访问文件系统、进程对象、SQLite 或任意网络地址。
2. 预加载脚本通过 `contextBridge` 暴露少量领域方法，如 `auth.login`、`daily.list`、`export.saveDailyReports`，不暴露原始 `ipcRenderer`。
3. Electron 主进程中的 NestJS `ApiClientService` 只访问启动时确定的 `127.0.0.1:<port>/api/v1`，不接受渲染进程传入任意 URL。
4. JWT 由主进程保存，API 请求由主进程附加 `Authorization`，渲染进程不持久化 JWT。
5. FastAPI 是唯一数据库访问者；Electron/NestJS 不加载 SQLite 驱动。

### 4.2 本地进程启动

1. Electron 获取单实例锁，防止两个客户端同时启动两套本地服务。
2. 主进程解析用户数据目录，准备数据库、日志、配置和导出临时目录。
3. `BackendProcessService` 选择可用端口，生成一次性启动握手值，以子进程方式启动 FastAPI sidecar，仅绑定 `127.0.0.1`。
4. 主进程轮询 `/health/ready`；数据库迁移、默认配置和首个模板初始化成功后服务才返回 ready。
5. 服务就绪后创建窗口；失败时展示可诊断错误页及日志位置，不显示空白窗口。
6. 应用退出时先停止接收新 IPC，再等待当前保存操作结束，最后优雅停止 FastAPI 子进程。

## 7. 权限与认证设计

### 7.1 角色权限

| 能力 | admin | user |
|------|-------|------|
| 登录、修改自己的密码 | 是 | 是 |
| 管理自己的日报、模板、周报、设置和导出 | 是 | 是 |
| 查看其他用户的日报和周报 | 否（首期） | 否 |
| 创建、启停用户、设置角色、重置密码 | 是 | 否 |
| 删除最后一个可用管理员 | 否 | 否 |

管理员不默认拥有查看他人工作内容的权限，减少不必要的数据暴露。如后续需要团队管理，应作为独立需求增加授权策略和审计。

### 7.2 首次启动

- `GET /api/v1/bootstrap/status` 返回是否需要初始化，不返回用户详情。
- 数据库没有用户时，允许使用一次性启动握手值调用 `POST /api/v1/bootstrap/admin` 创建首个管理员。
- 创建完成后接口永久关闭；并发请求由事务和唯一约束保证只成功一次。

### 7.3 JWT

- JWT 至少包含 `sub`（用户 ID）、`role`、`token_version`、`iat`、`exp`、`jti`。
- `exp` 固定为签发后 24 小时；不在首期引入 refresh token。
- 用户表保存 `token_version`。修改/重置密码、禁用用户时递增该值；每次受保护请求将令牌值与数据库当前值比较。
- JWT 密钥首次启动时随机生成，保存在用户数据目录的受限配置中，不写入源码、日志或渲染进程。
- 登录错误统一提示“用户名或密码错误”，避免枚举账号；连续失败进行短时退避/限流。
- 密码只保存 Argon2 哈希。管理员重置密码后要求用户下次登录修改密码。

## 8. 日报与周报核心流程

### 8.1 日报状态机

```text
create/save             submit（auto_archive=false）       archive
   ┌───────┐           ┌───────────┐                     ┌──────────┐
   │ draft │──────────▶│ submitted │────────────────────▶│ archived │
   └───────┘           └───────────┘                     └──────────┘
       │ submit（auto_archive=true）                           │
       └──────────────────────────────────────────────────────▶
```

- `draft`：允许修改工作日期和字段值，但修改日期也必须满足用户+日期唯一约束。
- `submitted`：内容不可直接编辑；第一版可继续执行归档，不提供退回草稿。
- `archived`：完全只读，可查询、导出、作为周报来源。
- 提交接口在一个事务内完成必填校验和状态转换。开启自动归档时，状态直接由 `draft` 变为 `archived`，同时写入 `submitted_at` 和 `archived_at`，不产生中间可见状态。
- 所有状态接口都校验当前状态；重复请求返回当前资源或明确的状态冲突，不重复写事件。

### 8.2 模板快照

创建日报时，在同一事务中读取当前启用模板，将每个启用字段复制到 `daily_report_fields`。快照包含稳定键、显示名称、类型、选项、是否必填、顺序和值。模板后续修改不更新快照。

两个核心字段稳定键固定为 `today_work` 和 `tomorrow_plan`。它们可调整标签、说明、顺序和必填属性，但不能删除、停用或改变字段类型。自定义字段可停用；已有日报快照不受影响。

首期字段类型支持：`text`、`textarea`、`number`、`date`、`single_select`、`multi_select`、`checkbox`。不支持附件和富文本。字段值以 JSON 保存，并由字段类型对应的 Pydantic 模型校验，避免全部退化为不可控字符串。

### 8.3 周报生成

1. 前端传入该周任意日期或规范化后的 `week_start`。
2. 后端统一以 `Asia/Shanghai` 计算周一、周日，禁止由客户端自行拼接范围。
3. 预览接口返回已归档来源、未归档提示和拟生成内容，不写数据库。
4. 生成接口查询并锁定逻辑来源，按工作日期升序形成规则化快照：
   - “本周日报汇总”：按日期列出每份日报的所有非空字段；
   - “本周工作内容”：按日期汇总 `today_work`；
   - “后续工作计划”：按日期汇总 `tomorrow_plan`；
   - “补充说明”：空白可编辑区。
5. 保存周报、来源关联和第一个版本。来源快照保留生成时日报字段，确保以后可审计。
6. 用户编辑只修改周报当前内容并新增版本，不反向修改日报或原始生成快照。
7. 重新生成必须提交当前 `version` 和 `confirm=true`；后端先保存旧内容版本，再生成新内容，版本号递增。版本恢复 UI 属于 P2，但数据层从首期开始保留版本。

## 9. API 设计

### 9.1 通用约定

- 根路径：`/api/v1`；健康检查使用 `/health/live` 和 `/health/ready`。
- JSON 使用 `snake_case`；时间使用带时区的 ISO 8601 字符串；纯工作日期使用 `YYYY-MM-DD`。
- 列表响应统一为 `{ "items": [], "page": 1, "page_size": 20, "total": 0 }`。
- 错误响应统一为：

```json
{
  "error": {
    "code": "DAILY_REPORT_INVALID_STATE",
    "message": "当前状态不允许归档",
    "details": {},
    "trace_id": "..."
  }
}
```

- 更新接口使用 `version` 做乐观锁。版本不匹配返回 HTTP 409，防止多个窗口或延迟请求静默覆盖。
- 400 表示请求语义错误，401 未登录/令牌失效，403 无权限，404 不存在，409 唯一性/状态/版本冲突，422 字段校验错误，501 表示预留能力尚未实现。

### 9.2 认证与用户

| 方法 | 路径 | 权限 | 说明 |
|------|------|------|------|
| GET | `/bootstrap/status` | 公开+本机握手 | 查询是否需创建首个管理员 |
| POST | `/bootstrap/admin` | 仅未初始化+握手 | 创建首个管理员 |
| POST | `/auth/login` | 公开 | 用户名密码登录，返回 24 小时 JWT 和用户摘要 |
| GET | `/auth/me` | 登录 | 返回当前用户和权限 |
| POST | `/auth/change-password` | 登录 | 校验旧密码，修改密码并使全部旧 JWT 失效 |
| GET | `/users` | admin | 分页查询用户 |
| POST | `/users` | admin | 创建用户 |
| PATCH | `/users/{id}` | admin | 修改显示名、角色、启停状态 |
| POST | `/users/{id}/reset-password` | admin | 重置密码并递增令牌版本 |

登录请求：

```json
{ "username": "alice", "password": "********" }
```

登录响应：

```json
{
  "access_token": "...",
  "token_type": "bearer",
  "expires_in": 86400,
  "user": { "id": 1, "username": "alice", "display_name": "Alice", "role": "user" }
}
```

### 9.3 个人设置与模板

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/settings/me` | 读取当前用户设置 |
| PATCH | `/settings/me` | 更新自动归档等可编辑设置 |
| GET | `/templates/current` | 读取当前日报模板及字段 |
| PUT | `/templates/current` | 整体保存模板配置，提交 `version` 防止覆盖 |

设置示例：

```json
{
  "auto_archive_on_submit": true,
  "timezone": "Asia/Shanghai",
  "week_starts_on": 1,
  "version": 2
}
```

模板字段请求结构：

```json
{
  "name": "默认日报模板",
  "version": 3,
  "fields": [
    {
      "id": 10,
      "key": "today_work",
      "label": "今日工作内容",
```

## 11. Excel 导出设计

- 入口支持明确 ID 列表和当前筛选条件两种模式，后端重新执行权限和归档状态校验。
- 首期单次最大导出 5,000 份；超过限制返回可理解错误，避免桌面进程长时间占用大量内存。
- 工作表“日报记录”每份日报一行。固定列为：工作日期、状态、提交时间、归档时间；随后是动态字段并集。
- 动态列使用稳定 `field_key` 合并；显示名相同但稳定键不同的字段分列，必要时在表头附加短标识，避免覆盖。
- 列顺序：固定列 → 两个核心字段 → 其余字段按首次出现日期和快照顺序排列。
- 多选值使用换行连接；日期和数字写入对应 Excel 类型；空值保持空白。
- 文本以 `= + - @` 开头时作为纯文本写入，防止公式注入；文件名和工作表名过滤非法字符。
- 表头加粗、冻结首行、自动筛选、合理列宽和自动换行。导出临时文件成功写完后再由 Electron 原子移动到用户选择的位置。
- 用户取消保存不记为错误；写入失败时删除本次临时文件并保留后端数据不变。

## 12. SQLite 与事务设计

- FastAPI 单实例持有数据库，Electron 不直接连接；不允许多个 worker 进程并发写同一 SQLite 文件。
- 每个请求独立 SQLAlchemy Session，Service 控制事务边界；创建日报、提交/自动归档、周报生成均在单事务完成。
- 连接初始化执行 `PRAGMA foreign_keys=ON`、合理的 `busy_timeout`，并使用 WAL 模式改善读写并行。
- 唯一性必须由数据库约束兜底，不只依赖“先查询后写入”。捕获约束错误后映射为 409 业务错误。
- 删除用户采用停用而非物理删除；日报、周报首期不提供物理删除 API。
- Alembic 迁移在后端 ready 前执行。迁移失败时禁止启动业务页面，并提示备份数据库及查看日志。
- 数据库位于 Electron `userData` 下的应用专属目录；日志、JWT 密钥、数据库和配置分开存放。
- 每次应用升级迁移前创建带版本号的数据库备份；只保留最近若干份，保留数作为配置常量。

## 13. 安全设计

- BrowserWindow 设置 `nodeIntegration=false`、`contextIsolation=true`、启用 sandbox；渲染层设置严格 CSP，禁止内联脚本和任意远程代码。
- 预加载只暴露具体业务方法，每个 IPC handler 校验来源窗口、通道和参数；不提供任意命令、文件路径或 HTTP 代理能力。
- FastAPI 仅绑定回环地址，并校验主进程启动握手；CORS 不向任意来源开放。
- JWT 加密保存在 Electron 主进程可访问的位置，优先使用 `safeStorage`；日志对 Authorization、密码和敏感正文脱敏。
- 所有资源查询先按 `owner_id=current_user.id` 限定，不能先按 ID 查询后在响应阶段过滤。
- 管理员操作必须同时检查角色和目标约束，尤其禁止停用/降级最后一个启用管理员。
- Excel 导出进行公式注入防护；文件保存只使用用户通过系统对话框选择的路径。
- 企业微信占位模块不包含真实地址、密钥或网络请求代码。
- 打包时禁用 Electron 远程模块，不加载网络 URL，不允许渲染层动态执行字符串代码。

## 14. 错误处理与可观测性

- 每个 API 请求生成 `trace_id`，Electron 主进程日志和 FastAPI 日志共同记录该值，便于关联问题。
- 日志采用结构化格式并按大小轮转；生产日志不记录密码、JWT、完整日报字段值或 Excel 内容。
- FastAPI 全局异常处理器将预期业务异常映射为稳定错误码，未知异常返回通用提示并记录堆栈。
- Electron 将后端未启动、令牌失效、版本冲突、校验错误和网络中断映射为不同用户提示。
- 401 时主进程清理本地令牌并通知渲染层跳转登录；409 版本冲突提示用户重新加载，不自动覆盖。
- `/health/live` 只说明进程存活；`/health/ready` 验证迁移完成和数据库可执行简单查询，但不泄露路径和配置。

## 15. 测试方案

### 15.1 后端单元与集成测试

- 认证：首个管理员并发初始化、登录成功/失败、24 小时过期、密码修改后旧令牌失效、禁用用户失效。
- 权限：普通用户无法管理用户；任一角色无法读取或修改他人日报/模板/周报；最后管理员保护。
- 模板：默认核心字段、字段类型校验、核心字段保护、版本冲突、修改后历史日报快照不变。
- 日报：日期唯一、草稿保存、必填校验、所有非法状态转换、自动归档原子性、重复操作幂等结果。
- 周报：周范围计算、只含归档日报、空周、来源提示、唯一周报、编辑不改日报、重生成版本留存。
- 导出：动态字段并集、不同模板版本、数据类型、中文、公式注入、非归档拒绝、越权和数量限制。
- 数据库：唯一键、外键、迁移、事务回滚和版本升级备份。

### 15.2 桌面端测试

- 渲染层组件：动态模板表单、校验反馈、状态按钮、筛选、周报编辑和空数据页面。
- NestJS 主进程：后端子进程启停、ready 超时、令牌安全存储、IPC 参数校验、API 错误映射、导出取消。
- 安全：渲染进程无法访问 Node 全局、原始 IPC、任意文件路径或任意 URL。
- E2E 主路径：首次创建管理员 → 登录 → 配置模板 → 创建日报 → 提交/归档 → 导出 → 生成并编辑周报。
- E2E 异常路径：重复日期、必填缺失、旧版本保存、后端异常退出、过期令牌和导出路径不可写。

### 15.3 验收门槛

- 后端与桌面端 lint、类型检查和自动测试全部通过。
- 数据迁移可从空库完成，也可对上一发布版本的数据库升级并保留数据。
- Windows 安装包在未安装 Python/Node 的干净环境可安装、启动、登录和完成核心路径。
- 核心业务规则必须有服务层测试，不能只依赖 E2E 覆盖。

## 16. 打包、部署与数据目录

- 开发环境：`uv sync` 安装后端依赖，Node 包管理器安装桌面依赖；统一开发命令并行启动 FastAPI 和 Electron/Vite。
- 发布环境：PyInstaller 将 FastAPI、迁移和 Python 运行时打为 sidecar；electron-builder 将 sidecar 放入应用 resources，并生成 Windows 安装包。
- 主进程不能假定当前工作目录，所有资源通过 `process.resourcesPath` 和 Electron API 解析绝对路径。
- SQLite、密钥、配置、日志放在可写 `userData`，绝不放进只读安装目录。
- 开发数据库与生产数据库使用不同应用目录和显式环境标识，避免测试污染真实数据。
- 首期不实现云同步。卸载应用默认不自动删除用户数据；彻底清理应提供单独、带确认的操作。

## 17. 关键设计决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| FastAPI 与 NestJS 职责 | FastAPI 唯一业务后端；NestJS 仅作 Electron 主进程容器 | 避免双业务后端和重复接口，同时保留指定框架 |
| 渲染 UI 框架 | Vue 3 + TypeScript | Vite 本身不是 UI 框架；Vue 适合表单和管理界面 |
| 渲染进程访问 API | 通过受控 IPC，由主进程调用 FastAPI | JWT 不暴露给渲染持久层，限制任意网络访问 |
| SQLite 写入者 | 单个 FastAPI 进程 | 避免 Electron/NestJS 与 Python 同时写库造成锁竞争和规则分散 |
| ORM 模式 | SQLAlchemy 同步 Session、单 worker | 个人规模下更简单稳定；异步不会给 SQLite 带来实际写并行收益 |
| 日报字段 | 规范化快照行 + JSON 类型值 | 支持动态字段、历史模板快照、类型校验和 Excel 动态列 |
| 核心模板字段 | 稳定键且不可删除/停用/改类型 | 保证周报汇总规则和默认模板语义稳定 |
| 日报唯一性 | 数据库唯一约束 `(owner_id, work_date)` | 并发或重复点击仍不会生成重复日报 |
| 自动归档 | 提交事务中直接完成 | 避免已提交中间状态和二次请求失败造成不一致 |
| 周报重新生成 | 显式确认并保存旧版本 | 防止人工修订被静默覆盖，同时控制首期 UI 复杂度 |
| 周报来源 | 已归档日报快照 | 结果可追溯，且不受后续模板配置影响 |
| JWT 失效 | `token_version` 每请求比对 | 满足密码修改后全部旧令牌立即失效，无需维护黑名单 |
| Excel 结构 | 一日报一行、字段并集 | 便于筛选、统计和跨模板版本导出 |
| 企业微信 | 能力查询 + 501 占位 | 保持清晰扩展边界，不制造虚假同步状态 |

## 18. 风险与待确认项

1. “NestJS”可能是“Next.js”的笔误。本方案按 NestJS 字面含义处理并将其用于 Electron 主进程；如实际指 Next.js，应在编码前调整渲染层方案。
2. Vite 未指定 UI 框架，本方案补充 Vue 3、Pinia、Vue Router、Element Plus；如团队偏好 React，需要在代码实现前替换，后端和数据模型不受影响。
3. 本地多用户仅能隔离应用内访问，拥有 Windows 用户目录和数据库文件权限的人仍可能复制数据库。若要求不同人员强隔离，应采用各自 Windows 账户或远程服务端部署。
4. Electron `safeStorage` 的保护强度依赖操作系统账户。应用内多用户共享同一 Windows 账户时，不等同于企业级密钥保险库。
5. 允许未来日期日报可能导致周报提前包含未来记录；本方案严格按工作日期和归档状态汇总，不额外排除未来日期。
6. 首期字段类型已选定但需求只明确“可配置字段”。如只需要文本，可缩减实现；附件和富文本明确不进入首期。
7. SQLite 适合个人/单机多用户，不适合多台客户端同时连接共享数据库文件；未来远程部署应迁移 PostgreSQL，而不是把 SQLite 放到网络共享盘。

## 19. 实现计划

1. 工程骨架与契约：建立 monorepo、FastAPI/uv、Electron/Vite/NestJS、质量工具、OpenAPI 类型生成和统一开发命令。
2. 数据基础：实现 SQLAlchemy 模型、Alembic 初始迁移、SQLite 初始化参数、默认数据和仓储基类。
3. 认证与桌面启动：完成首次管理员、JWT、角色、密码失效机制，以及 Electron 启动/健康检查/安全 IPC/令牌保存。
4. 模板与设置：实现默认模板、动态字段配置、核心字段保护、个人自动归档设置和相应 UI。
5. 日报闭环：实现创建、编辑、查询、提交、自动/手动归档、状态机、模板快照和权限测试。
6. Excel 导出：实现归档校验、动态字段并集、安全工作簿生成、Electron 保存对话框和失败恢复。
7. 周报闭环：实现自然周预览、生成、来源快照、人工编辑、版本、重生成确认和来源追溯。
8. 管理与占位：实现用户管理、审计关键事件和企业微信不可用入口。
9. 集成与验收：完成单元、API、组件及 Electron E2E 测试，修复契约和交互问题。
10. 发布：完成 PyInstaller sidecar、electron-builder Windows 安装包、迁移备份、干净环境冒烟测试和使用说明。

## 20. 代码实现阶段交付顺序

建议按可运行的垂直切片交付，而不是一次性铺开全部页面：

- 里程碑 A：桌面应用可启动、FastAPI 可健康检查、可创建首个管理员并登录。
- 里程碑 B：默认模板可用，用户可创建、保存、提交和归档一份日报。
- 里程碑 C：日报筛选与 Excel 导出可用。
- 里程碑 D：指定自然周可生成、编辑、保存和重新生成周报。
- 里程碑 E：模板配置、用户管理、安全加固、打包和完整验收完成。

每个里程碑都应包含数据库迁移、后端测试、前端交互和最小 E2E，不将测试与打包集中拖到项目末尾。
