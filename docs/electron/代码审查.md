### 问题清单

#### 🔴 严重问题（P0/P1）

**P1-01：工程仍声明并使用不受支持的 Node 20 基线**

- 位置：`package.json:19`、`electron/README.md:17`
- 触发场景：开发者按仓库声明使用 Node 20.19 执行干净安装、后续原生依赖重建或打包。
- 实际影响：根 `engines.node` 和 README 与 ADR-013、`architecture.md`、`coding-rule.md` 的 Node.js 22.12+ 固定基线冲突；本次 `npm ci` 已对 `@electron/rebuild` 和 `node-abi` 给出 `EBADENGINE`。当前通过的 typecheck/lint/build 不能替代受支持工具链验证，原生重建或 PKG-01 可能失败。
- 建议方向：将根 `engines.node` 和所有使用说明统一为 `>=22.12.0`，在 Node.js 22.12+ LTS 上重新执行 `npm ci`、typecheck、lint、build 和必要 smoke，要求不再出现 engine 警告。若根约束修订仍由 GOV-01 承担，必须先由技术负责人记录明确例外和提前执行顺序；不能继续把升级仅推迟到 PKG-01。

**P1-02：导航白名单可被前缀绕过，生产态还放行任意本地文件**

- 位置：`electron/src/main/index.ts:34`
- 触发场景：开发态导航到 `http://localhost:5173@evil.example/`，或生产态导航到任意 `file:///C:/...` URL。
- 实际影响：前者的真实 origin 是 `http://evil.example`，但 `startsWith(devUrl)` 返回 true；后者因只判断 `startsWith('file:')` 而全部放行。这违反“只加载受控 dev 地址或应用自身资源”的冻结安全契约，可能把 BrowserWindow 导向外部页面或非应用本地文件。
- 建议方向：使用 `new URL()` 解析并精确比较 dev origin、协议、主机和端口；生产态只允许解析后的目标等于应用自身 renderer 入口，或在首次加载完成后拒绝所有顶层导航。将恶意 userinfo URL、相似前缀域名、任意本地文件和合法目标加入自动化回归测试，禁止继续用字符串前缀作为安全边界。

#### 🟡 建议修改（P2）

**P2-01：仓库默认使用第三方二进制镜像，但缺少信任与完整性决策**

- 位置：`.npmrc:1`、`electron/electron-builder.yml:22`、`build/THIRD-PARTY-LICENSES.md:10`
- 触发场景：干净环境安装 Electron，或 electron-builder 下载打包辅助二进制。
- 实际影响：这些二进制从 `npmmirror.com` 下载，不受 npm lock 中 tarball integrity 的同一条校验链保护；许可证文档称其“仅网络加速，不改变来源”不足以表达实际下载来源和信任边界。
- 建议方向：优先恢复官方默认下载源；若项目必须使用镜像，先形成明确批准的镜像信任、校验和 CI/发布策略，并把镜像限定为可覆盖的本地/CI 配置，而非无条件写入发布构建配置。

**P2-02：开发态 CSP 放行项被原样带入生产构建**

- 位置：`electron/src/renderer/index.html:6`
- 触发场景：生产 renderer 中发生脚本注入或依赖被利用后发起本机网络请求。
- 实际影响：生产产物仍允许任意端口的 `ws://localhost:*`、`http://localhost:*` 和 `http://127.0.0.1:*`，并允许 `style-src 'unsafe-inline'`，扩大本机服务探测/访问面，与“生产严格 CSP”目标不完全一致。
- 建议方向：拆分 dev/production CSP；开发态只放行 electron-vite HMR，生产态仅放行应用资源和当次 sidecar 的精确 origin。动态端口策略应在 DESK-02/DESK-03 契约中实现，不应永久放行全部本机端口。
