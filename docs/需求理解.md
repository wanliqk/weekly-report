# 个人日报周报管理系统需求文档（第一版）

## 需求概述

建设一个面向个人使用的日报、周报管理系统。用户可按工作日期创建日报草稿，基于模板填写内容，经过提交和归档后沉淀为可查询、可导出的个人工作记录；系统可按指定自然周汇总日报并生成周报，周报生成后允许人工补充和修订。系统同时保留企业微信日报同步入口及后续扩展边界，但本期不连接企业微信，也不执行实际同步。

## 用户与使用场景

- 目标用户：需要持续记录每日工作并按周整理汇报的个人用户。
- 日常记录：用户每天创建或继续编辑当日（也可选择其他工作日期）的日报草稿，填写后提交、归档。
- 历史检索：用户按日期范围、状态等条件查找过往日报，并查看详情。
- 记录导出：用户选择已归档日报导出为 Excel，作为离线留存或二次整理材料。
- 周度汇总：用户选择一个自然周，系统汇总该周日报生成周报，再由用户人工补充、修订和保存。
- 模板维护：用户调整后续日报使用的字段、顺序等配置，以适应个人记录习惯。

## 核心业务对象与规则

### 日报

- 每份日报归属于一个工作日期；默认约束为同一用户、同一工作日期仅有一份日报。
- 日报生命周期为“草稿 → 已提交 → 已归档”。草稿可反复保存；提交表示内容填写完成；归档表示内容成为正式个人记录。
- 已归档日报默认只读，避免历史记录被无意修改；是否支持撤回归档列为待确认项。
- 日报记录创建时保存当时的模板字段快照。后续修改模板不得改变既有日报的字段、内容或展示结果。
- 日报至少记录：工作日期、模板字段及内容、当前状态、创建时间、更新时间、提交时间、归档时间。

### 日报模板

- 系统初始化一套默认日报模板，包含“今日工作内容”和“明日工作计划”两个内容项。
- 用户可以维护用于新建日报的模板，包括新增字段，以及调整字段名称、说明、顺序、是否必填和启用状态。
- 第一版暂定两个默认内容项为核心字段，可以调整展示配置，但不得同时停用或删除；该规则需用户确认。
- 模板调整仅影响调整后新建的日报，不追溯修改已经创建的日报。

### 周报

- 周报以用户指定的自然周为统计周期。第一版暂定自然周为周一 00:00 至周日 23:59（Asia/Shanghai）。
- 周报主要汇总该自然周内已归档日报；未归档日报不作为正式汇总来源，并在生成时提示用户。
- 周报生成内容应能追溯到来源日报，至少保留统计周期、来源日报标识/日期及生成时间。
- 同一自然周默认仅保留一份当前周报，防止重复生成造成记录混乱。
- 自动汇总结果生成后可由用户人工补充和修订；保存人工修订时不得反向修改来源日报。
- 如提供“重新生成”，必须在覆盖人工修订前明确提示并由用户确认；具体采用覆盖还是版本留存列为待确认项。

## 输入与输出

### 输入

- 日报工作日期。
- 日报模板字段配置。
- 日报各字段的文本内容。
- 日报查询条件，如日期范围和状态。
- Excel 导出的日报选择范围。
- 周报对应的自然周及人工补充、修订内容。

### 输出

- 可保存、提交、归档和查看的日报记录。
- 满足筛选条件的日报列表和日报详情。
- 包含已归档日报数据的 Excel 文件。
- 指定自然周的自动汇总周报及人工修订后的周报内容。
- 企业微信同步功能入口及“本期暂不可用”的清晰状态说明。

## 功能需求

### P0 - 必须实现

- [ ] 日报草稿创建：用户可选择工作日期，按当前启用的日报模板创建草稿；同一工作日期重复创建时应进入已有日报或给出明确提示。
- [ ] 日报草稿编辑与保存：用户可填写模板字段并多次保存，刷新或重新进入后内容不丢失。
- [ ] 日报提交：系统校验必填字段，通过后将草稿变更为已提交并记录提交时间；校验失败时明确标出缺失内容。
- [ ] 日报归档：用户可将已提交日报归档，系统记录归档时间，并将其纳入正式历史记录和周报数据来源。
- [ ] 日报列表与详情：用户可查看日报的工作日期、状态、更新时间等摘要，并进入详情查看完整字段内容。
- [ ] 日报查询：用户可至少按工作日期范围和状态筛选日报，并可清除筛选条件恢复完整列表。
- [ ] 默认日报模板：系统首次使用时提供“今日工作内容”和“明日工作计划”两个内容项，用户无需配置即可创建日报。
- [ ] 日报模板配置：用户可新增字段，并调整字段的名称、说明、顺序、是否必填和启用状态；保存后用于新建日报。
- [ ] 模板快照：日报创建后不因模板后续修改而丢失字段或改变历史内容。
- [ ] 已归档日报 Excel 导出：用户可按筛选结果或勾选记录导出已归档日报；非归档记录不得混入导出结果。
- [ ] 自然周选择：用户可指定一个自然周查看其起止日期及可用日报情况。
- [ ] 周报自动生成：系统按指定自然周汇总已归档日报，生成结构清晰、可继续编辑的周报初稿。
- [ ] 周报编辑与保存：用户可在自动汇总结果基础上补充、修订并保存，且不改变来源日报。
- [ ] 周报查询与详情：用户可按自然周查看已生成周报及其当前内容。
- [ ] 企业微信同步占位：日报相关页面保留同步入口；用户触发时仅提示“功能暂未开放”，不得调用外部接口或宣称同步成功。

### P1 - 重要功能

- [ ] 操作确认与反馈：提交、归档、重新生成等关键操作提供明确确认或结果反馈，避免误操作。
- [ ] 未归档提示：生成周报时展示该周草稿、已提交但未归档日报的数量或日期，帮助用户补齐记录。
- [ ] 空数据处理：没有日报的自然周仍可创建空白周报并人工填写，同时明确提示本次没有可汇总日报。
- [ ] 导出可读性：Excel 包含工作日期、各模板字段、状态及关键时间等列；动态模板字段应有稳定、可理解的列名。
- [ ] 数据追溯：周报详情可查看本次汇总所依据的日报日期或跳转到来源日报。

### P2 - 可选功能

- [ ] 日报快速复制：可复制上一工作日或指定日报的内容创建新草稿。
- [ ] 周报生成预览：保存前预览来源日报和汇总结果。
- [ ] 周报版本记录：保存自动生成及人工修订的历史版本，并支持比较或恢复。
- [ ] 更多导出方式：支持周报 Excel/PDF 或日报自定义列导出。
- [ ] 企业微信实际同步：在后续版本完成授权、字段映射、提交、结果记录及失败重试。

## 非功能需求

- 易用性：首次进入即可使用默认模板创建日报；核心操作名称和状态含义一致，错误提示应说明原因和处理办法。
- 数据完整性：日报状态变更、模板快照、周报来源关系和人工修订内容必须可靠保存；重复点击不得产生重复日报、重复归档或重复周报。
- 性能：在个人常规数据规模下，列表查询、日报保存、周报读取等常用操作应在 2 秒内反馈；Excel 生成应展示处理中状态并在合理时间内完成。
- 安全与隐私：工作记录只对当前用户可见；输入、查询和导出接口需校验访问权限，避免越权读取或修改数据。
- 可恢复性：保存失败、网络异常或导出失败时不得错误变更状态，应保留用户已填写内容并允许重试。
- 可维护性：模板字段和企业微信同步能力应具备稳定的数据标识及清晰边界，以支持后续扩展，而不破坏既有日报数据。
- 兼容性：具体运行平台、浏览器或移动端适配范围尚未确定，需在方案设计前确认。

## 边界与约束

- 本期不实现企业微信授权、接口调用、真实同步、同步结果回写及失败重试。
- 本期面向个人记录，不包含团队成员管理、上下级审批、评论、抄送、催办、组织统计或绩效评估。
- 本期不包含从企业微信或其他系统导入历史日报。
- 本期不要求智能总结、自然语言润色或其他 AI 生成功能；周报自动生成以规则化汇总日报为基础。
- 本期 Excel 导出范围仅包含已归档日报；周报导出属于可选扩展。
- 技术栈、部署方式、数据存储方式、备份策略及用户身份认证方式尚未指定，将在方案设计阶段确认。
- 系统时区第一版暂按 Asia/Shanghai，自然周暂按周一至周日计算。

## 验收标准

### 日报创建、保存与唯一性

- Given 用户尚未创建某工作日期的日报，When 用户选择该日期并创建，Then 系统使用当前启用模板生成草稿，并展示“今日工作内容”和“明日工作计划”。
- Given 某工作日期已经存在日报，When 用户再次尝试为同一日期创建，Then 系统不产生重复记录，并引导用户查看或编辑已有日报。
- Given 用户在草稿中填写内容并保存，When 用户刷新页面或重新进入该日报，Then 已保存字段及内容完整恢复。

### 日报提交与归档

- Given 草稿存在未填写的必填字段，When 用户提交，Then 系统阻止提交、保持草稿状态并指出缺失字段。
- Given 所有必填字段均符合要求，When 用户提交日报，Then 日报状态变为已提交，并记录准确的提交时间。
- Given 日报处于已提交状态，When 用户确认归档，Then 日报状态变为已归档、记录归档时间，并可用于查询、导出和周报汇总。
- Given 日报未处于已提交状态，When 用户尝试直接归档，Then 系统拒绝操作并说明允许的前置状态。

### 日报模板

- Given 用户未做任何模板配置，When 首次创建日报，Then 系统默认展示两个内容项且可正常填写和保存。
- Given 用户新增字段并调整字段顺序后保存模板，When 创建下一份日报，Then 新日报按最新配置展示字段及顺序。
- Given 某日报已经创建，When 用户修改或停用其来源模板中的字段，Then 该日报原有字段和值保持不变并仍可正常查看。

### 日报查询

- Given 系统中存在不同日期和状态的日报，When 用户设置日期范围和状态条件，Then 列表只显示同时满足条件的记录。
- Given 用户清除筛选条件，When 列表重新加载，Then 系统恢复显示当前用户的全部日报，并保持明确排序。

### Excel 导出

- Given 用户选择了一组已归档日报，When 发起导出，Then 系统生成可被常用 Excel 软件正常打开的文件，且每份日报的数据完整、列名清晰。
- Given 导出选择中包含草稿或已提交未归档日报，When 发起导出，Then 系统排除或拒绝这些记录并明确提示，不得将其写入归档导出文件。
- Given 不同日报使用过不同版本模板，When 合并导出，Then 各日报已有字段和值不丢失，缺少某字段的记录以空值呈现。

### 周报生成与修订

- Given 指定自然周内存在已归档日报，When 用户生成周报，Then 系统只汇总工作日期位于该周的已归档日报，并记录来源日期和生成时间。
- Given 指定周存在草稿或已提交未归档日报，When 用户生成周报，Then 系统不把这些日报作为正式来源，并清晰提示其数量或日期。
- Given 指定周没有已归档日报，When 用户创建周报，Then 系统提示无可汇总数据，并允许用户创建、编辑和保存空白周报。
- Given 周报已自动生成，When 用户补充或修改内容并保存，Then 再次打开时显示修订后的内容，来源日报内容保持不变。
- Given 同一自然周已存在周报，When 用户再次请求生成，Then 系统不静默创建重复周报或覆盖人工内容，而是提供查看现有周报或确认重新生成的路径。

### 企业微信同步占位

- Given 用户看到企业微信同步入口，When 用户点击该入口，Then 系统明确提示功能暂未开放，不发起任何企业微信请求，也不改变日报状态。

### 异常与权限

- Given 日报保存、状态变更或导出过程中发生网络或服务异常，When 操作失败，Then 系统显示失败原因或重试提示，不错误显示成功，不产生重复数据。
- Given 用户请求访问不属于自己的日报、模板、周报或导出结果，When 系统处理请求，Then 拒绝访问且不泄露记录内容。

## 待确认问题与当前假设

1. 运行形态：是桌面浏览器 Web 系统、移动端 H5、小程序，还是需要多端适配？Electron
2. 用户身份：是否需要账号登录，还是仅供本机单人使用？需要登陆。认证方式：JWT (24h 有效期，密码修改后自动失效)，支持多用户角色 (admin/user)
3. 日报日期：是否允许补写未来日期或历史日期？允许补写未来日期或历史日期，但是如果当日已经存在已归档的日报则不可补写。
4. 状态流转：已提交是否必须由用户再次操作才归档？已提交或已归档是否允许撤回？本文暂按提交、归档为两个独立动作，归档后只读。系统支持设置提交后自动归档。
5. 默认字段：两个默认内容项能否删除、停用或改名？本文暂按核心字段不可同时停用或删除，但允许调整展示配置。
6. 字段类型：除多行文本外，模板是否需要单行文本、数字、日期、单选、多选或附件？本文暂不限定具体字段类型。
7. 周报结构：期望按日期罗列，还是归并为“本周完成/下周计划/问题风险”等栏目？本文只要求规则化、可编辑汇总，具体格式待确认。
8. 周报来源：是否应纳入“已提交但未归档”的日报？本文暂以已归档日报作为唯一正式来源。
9. 重新生成：周报人工修改后再次生成，是覆盖、合并还是创建新版本？本文要求不得静默覆盖，具体策略待确认。
10. Excel 规格：是每份日报一行、每份日报一个工作表，还是需要固定企业格式？本文暂按适合筛选统计的表格导出，具体列结构待设计。
11. 数据规模与保留：预计日报年限、单次最大导出数量，以及是否需要定期备份或永久保留尚未明确。

# 日报、周报、账户与统计需求变更（第二版增量）

> 变更编号：CR-20260807-01
> 文档状态：需求已确认；推荐口径已作为第二版技术基线冻结
> 适用范围：替代第一版中“同一用户同一日期仅一份日报”“单篇日报独立归档”“首次启动创建首位管理员”及相关自动归档规则；未被本节替代的第一版要求继续有效

## 需求概述

本次变更将日报从“每天只有一篇、逐篇归档”调整为“同一天可记录多篇日报条目，并在日期维度汇总归档为一篇正式日报”。桌面端同时统一菜单命名，补充管理员撤销提交、草稿删除、首次启动双账号初始化和个人统计能力。周报仍以正式归档日报为来源，并为后续接入 AI 自动生成保留产品边界，但本次不接入任何大模型服务。

为避免“日报”一词同时指多种对象，本节统一使用以下术语：

- **日报条目**：用户在某个工作日期下新建的一次记录，状态为草稿或已提交；同一天可以有多篇。
- **当日归档日报**：用户对某个工作日期执行归档后，由当天全部已提交日报条目汇总形成的唯一正式日报。
- **日期已归档**：该用户该工作日期已产生当日归档日报，日期被关闭，不得再创建新的日报条目。
- **完成日期**：已经形成当日归档日报的日期；仅有草稿或已提交条目不算完成。

## 用户与使用场景

- 普通用户在“我的日报”日历中查看每天是否有记录、记录数量和完成状态，并在未归档日期创建多篇日报条目。
- 普通用户可以反复保存或删除自己的草稿；提交后由管理员按权限撤销提交，普通用户不能自行撤销。
- 普通用户在当天条目均处理完毕后，通过日期级“归档”按钮把已提交条目汇总成一篇正式日报，并关闭该日期。
- 普通用户在“我的周报”中基于已归档日报生成、查看和编辑周报；未来可选择由 AI 基于日报生成周报。
- 管理员使用仅管理员可见的用户管理能力维护账号，并可撤销尚未进入当日归档日报的已提交条目。
- 登录用户在“统计”中查看自己的每日完成状态、月份完成率和记录概览；本次不提供管理员组织级统计。

#### 1. 菜单与页面命名

- [ ] Electron 菜单和对应页面标题将“日报工作台”统一改为“我的日报”。
- [ ] Electron 菜单和对应页面标题将“周报工作台”统一改为“我的周报”。

- [ ] “我的日报”默认展示当前月份的月历，并支持切换月份和选择具体日期。

#### 3. 同日多篇日报条目

- [ ] 同一用户、同一工作日期不再限制只能创建一篇日报条目；在日期未归档时，不设置业务篇数上限。
- [ ] 即使当天已存在一篇或多篇已提交条目，用户仍可继续创建新条目；已有草稿也不阻止创建。
- [ ] 每篇新条目仍使用创建当时的模板版本和完整字段快照，后续模板变更不得改变既有条目。
- [ ] 日期已归档后，创建入口禁用并明确提示“该日期已归档，不能继续创建日报”，服务端也必须拒绝绕过界面的创建请求。
- [ ] 并发或重复点击创建可以产生多篇真实的新条目，但一次请求不得因重试被意外重复执行；具体幂等方案在技术设计阶段确定。

#### 4. 草稿保存与删除

- [ ] 用户可以反复保存自己的草稿，并通过乐观锁避免旧页面覆盖新内容。
- [ ] 只有草稿状态的日报条目允许由其所有者删除；已提交条目和已进入当日归档日报的来源条目不得删除。
- [ ] 删除有内容的草稿前必须进行醒目确认；删除成功后从当天列表、日历数量和统计中移除。
- [ ] 删除失败时不得从界面提前移除条目或错误显示成功，用户应可重试。

#### 5. 提交与管理员撤销提交

- [ ] 草稿通过模板快照的必填和类型校验后可提交；提交后条目只读并记录提交时间。
- [ ] 普通用户不能自行撤销提交。
- [ ] 管理员可以将任意用户尚未归档的已提交条目撤销为草稿；日期已归档后不得撤销其中的来源条目。
- [ ] 撤销提交后清除本次提交时间，保留正文和模板快照，所有者可继续编辑并重新提交。
- [ ] 管理员撤销提交必须记录操作者、操作时间和原因；日志或审计信息不得记录日报正文。
- [ ] 管理员撤销提交后，日报所有者再次进入“我的日报”时必须能看到该条目已退回草稿及撤销原因。
- [ ] 管理员操作其他用户日报时只可见账号、工作日期、条目状态、条目标识、版本和提交时间等必要元数据；本次明确不开放其他用户正文或模板快照。

#### 6. 日期级汇总归档

- [ ] “我的日报”选中日期后始终显示日期级“归档”按钮；无可归档条目、存在未处理草稿或日期已经归档时，按钮显示对应禁用状态和原因。
- [ ] 日期级归档的对象是当前用户、所选工作日期下的全部已提交日报条目，不得混入其他日期、其他用户或草稿。
- [ ] 为避免归档后遗留无法处理的草稿，当前验收基线为：当天仍有草稿时阻止归档，并提示用户先提交或删除草稿。
- [ ] 至少存在一篇已提交条目且当天没有草稿时，用户确认归档后，系统按“提交时间升序、条目标识升序”的稳定顺序汇总全部条目，生成且仅生成一篇当日归档日报。
- [ ] 汇总结果必须保留每个来源条目的边界、字段标签、字段值、模板快照和来源标识；不同模板版本的字段不得丢失或被错误合并。
- [ ] 归档事务必须同时完成来源关系固化、正式日报生成、归档时间写入和日期关闭；任一步失败均不得留下部分归档结果。
- [ ] 来源条目在归档后保留为只读、可追溯记录，但不再作为独立的正式归档日报参与周报或导出，避免重复统计。
- [ ] 对同一日期重复归档或并发归档不得生成第二篇正式日报，应返回已有当日归档日报并明确提示日期已完成。
- [ ] 日期归档后不得新增条目、删除来源、撤销提交或修改正式日报；本次不提供撤销日期归档能力。
- [ ] 第一版“提交后自动归档”设置与同日多篇及日期级汇总冲突，本变更将其停用/移除；提交动作不得自动关闭日期。

#### 7. “我的周报”与未来 AI 扩展

- [ ] 现有周报列表、自然周选择、规则化生成、人工编辑、来源追溯和确认后重新生成能力继续保留，统一放在“我的周报”。
- [ ] 周报只读取每个完成日期唯一的当日归档日报，不直接读取草稿、待归档条目或归档来源条目，避免同一内容重复汇总。
- [ ] 周报来源详情应能跳转到当日归档日报，并可继续追溯其来源条目。
- [ ] 本次不接入 AI 大模型，不保存模型密钥，不发起模型网络请求；后续 AI 生成能力必须可由用户在“设置”中显式启用和配置。

- [ ] 普通用户创建成功的同一事务内，系统自动创建一个默认管理员账号；管理员用户名固定为 `admin`，初始密码固定为 `admin123`（不随首位用户设置的密码变化），两个账号的密码必须分别安全哈希保存。管理员首次登录必须先修改密码才能使用（见下一节），缓解固定初始密码带来的风险。
- [ ] 初始化过程必须是原子的：普通用户、默认管理员及各自默认设置/模板要么全部成功，要么全部失败；并发初始化不得产生多组默认账号。
- [ ] 首次普通用户的用户名不得与默认管理员用户名冲突；重复初始化必须安全失败。
- [ ] 用户管理提供查询、创建、编辑、密码重置、启用/停用和删除入口，并继续保护最后一个有效管理员。
- [ ] 删除用户属于高风险操作，必须醒目确认。当前安全基线为：无业务记录的账号允许物理删除；已有日报、周报、导出或其他业务记录的账号禁止物理删除，只允许停用。若需要级联清除全部数据，必须另行确认数据保留与恢复规则。
- [ ] 普通用户看不到用户管理菜单；对用户管理 API、管理员撤销提交 API 的越权调用返回权限不足且不得泄露账号或日报内容。

## 非功能需求

- **权限与隐私**：普通用户只能访问自己的日报、周报和统计；管理员新增的撤销提交权限遵循最小可见范围，未明确授权前不扩大为查看全部正文。
- **一致性**：同日多篇创建、草稿删除、管理员撤销、日期级汇总归档和统计更新必须由数据库约束、事务和乐观锁共同保证，不得产生重复正式日报或部分归档。
- **可追溯性**：当日归档日报必须能追溯到全部来源条目；管理员撤销提交和账号删除必须能追溯到操作者、时间和原因，但审计信息不得包含正文。
- **数据迁移**：现有“一天一篇”历史数据升级后不得丢失。已归档历史日报应迁移/映射为对应日期的当日归档日报；草稿和已提交历史日报映射为该日期的一篇日报条目。具体迁移在方案设计阶段定义并用真实旧库副本验证。
- **安全**：密码继续使用 Argon2id；JWT、`safeStorage`、回环地址、运行时密钥及 API 分层约束不变。默认管理员与普通用户共享初始密码不得导致明文复用或日志泄漏。
- **易用性**：所有日历状态均有文字或图标辅助，不能只依赖色彩；危险操作说明影响范围；无权限菜单不展示，直接访问仍由后端拒绝。
- **性能**：月历状态、统计卡片和所选日期条目在个人常规数据规模下 2 秒内反馈；查询必须按当前用户和日期范围收敛。

## 边界与约束

- 本次是需求整理，不包含代码实现、数据库迁移、API 改造或 Electron 页面修改。
- 本次不接入任何 AI 大模型、企业微信、节假日服务或外部统计平台。
- 本次统计仅针对当前用户，不提供管理员全员视图、排名或绩效判断。
- 当日归档日报是周报、Excel 导出和“完成日期”统计的唯一正式日报口径；来源条目不得重复参与这些正式结果。
- 归档后保持只读且不支持撤回；如后续需要纠错，必须设计版本、审计和重新汇总规则。
- 默认管理员账号命名、用户物理删除范围、管理员正文可见性和完成率自然日口径已按文末基线冻结；改变这些规则必须先更新需求与方案，未经迁移验证仍不得执行不可逆的数据结构变更。

## 验收标准

### 我的日报日历与同日多篇

- Given 某日期没有任何条目，When 用户打开“我的日报”，Then 该日期显示无日报状态，并可从该日期创建第一篇草稿。
- Given 某日期已有草稿或已提交条目且尚未归档，When 用户再次创建，Then 系统生成新的独立草稿，不跳转到旧条目，也不因同日已存在记录而拒绝。
- Given 同一天同时存在两篇草稿和一篇已提交条目，When 日历加载，Then 日期格同时显示三篇总数及对应状态，不误显示为已完成。
- Given 日期已经归档，When 用户从界面或 API 尝试创建新条目，Then 系统拒绝且不产生数据。

### 草稿删除与提交撤销

- Given 用户拥有一篇草稿，When 确认删除，Then 条目被删除，日历和统计数量刷新，其他条目不受影响。
- Given 条目已提交，When 所有者尝试删除或撤销，Then 系统拒绝并保持已提交状态。
- Given 管理员对尚未归档的已提交条目填写原因并撤销，When 操作成功，Then 条目回到草稿、正文保持不变、提交时间清除，所有者可看到撤销原因并继续编辑。
- Given 日期已经归档，When 管理员尝试撤销任一来源条目，Then 系统拒绝且正式日报不发生变化。

### 日期级归档

- Given 某日期仍有草稿，When 用户点击归档，Then 系统阻止操作并列出需要提交或删除的草稿数量。
- Given 某日期没有草稿且有多篇已提交条目，When 用户确认归档，Then 系统一次性生成一篇正式日报，按稳定顺序保留全部来源内容，并关闭该日期。
- Given 汇总中的任一步发生异常，When 事务回滚，Then 日期仍未归档、来源条目仍为原状态，不存在半成品正式日报。
- Given 两个归档请求并发到达，When 系统处理，Then 最终只有一篇当日归档日报，另一个请求获得已有结果或明确冲突。
- Given 日期归档成功，When 生成周报、导出 Excel 或计算完成率，Then 只使用该日期的一篇正式日报，不重复使用来源条目。

### 首次启动与用户管理

- Given 系统没有任何用户，When 用户提交普通账号初始化信息，Then 系统原子创建普通用户和默认管理员，管理员初始密码固定为 `admin123`（与用户输入密码无关）并单独哈希保存，登录后强制先改密。
- Given 两次初始化并发发生，When 事务完成，Then 系统只存在一组首次普通用户和默认管理员，不出现部分账号或重复默认管理员。
- Given 普通用户登录，When 打开主界面或直接访问用户管理路由/API，Then 菜单不显示且服务端拒绝访问。
- Given 管理员删除一个已有业务记录的用户，When 确认操作，Then 系统拒绝物理删除并提示改为停用，不丢失该用户历史数据。

### 统计

- Given 当前月截至今天共有 7 个自然日且 5 天已归档，When 统计页加载，Then 本月完成率显示为 `71.4%`，未来日期不计入分母。
- Given 某完成日期由 3 篇来源条目汇总归档，When 统计本月已写日报篇数，Then 计入 3 篇来源条目，不因汇总日报再额外计 1 篇。
- Given 用户今天未完成、昨天和前天均完成、大前天未完成，When 查看连续记录，Then 显示连续记录 2 天。
- Given 管理员打开统计页，When 请求统计数据，Then 仅返回管理员自己的数据，不返回其他用户统计。

### 周报与 AI 边界

- Given 一周内有多个完成日期且每个日期有一篇当日归档日报，When 生成周报，Then 每个日期只汇总一次，并能追溯到当日归档日报及其来源条目。
- Given 本次版本未配置 AI，When 用户使用“我的周报”，Then 继续使用现有规则生成能力，不发起任何大模型网络请求。

## 已冻结的第二版口径

1. **默认管理员**：用户名固定为 `admin`，首次普通用户不得使用归一化后相同的用户名；默认管理员首次登录必须改密，完成前不能使用业务能力。
2. **管理员撤销权限**：只开放账号、日期、状态、条目标识、版本和提交时间等必要元数据及撤销操作，不开放其他用户正文或模板快照。
3. **归档时存在草稿**：阻止归档，要求所有者先提交或删除草稿，不允许忽略草稿关闭日期。
4. **用户删除语义**：只物理删除完全没有业务记录的账号；有历史数据的账号只能停用，本次不做级联清除。
5. **统计口径**：完成率和连续记录按自然日，周末计入；日报篇数按已提交及已归档来源条目计数，日期级正式日报不重复计数。
6. **汇总展示格式**：正式快照按提交时间和条目标识稳定排序，界面按来源条目分段卡片展示，不在归档时把不同来源的同名字段压平。

以上口径已进入 `docs/方案设计.md` 的第二版技术方案。后续若改为自定义管理员、仅提醒改密、管理员查看正文、忽略草稿归档、级联删除或工作日统计，均属于产品/架构变更，需先评审权限、迁移和验收影响。

## 2026-08-08

# 企业微信日报反向同步需求变更（第三版增量，CR-20260808-02）

> 本节只定义新增范围，不改写第一版和第二版已经交付的历史事实。与既有“企业微信仅占位、不得发起外部请求”约束冲突时，以本节为后续版本的需求基线；在本增量代码交付前，当前产品仍保持占位行为。

## 1. 背景与目标

系统已经具备同日多篇日报条目、日期级归档和不可变正式快照，也已经在设置页预留企业微信入口。用户提供的 `backend/wx-ribao/wx-ribao.py` 已验证企业微信网页登录 Cookie 获取、文档 Cookie 保存、日报模板/历史数据读取和内部接口解析；`http_raw_request.txt`、`http_raw_response.txt` 提供了一次真实提交的协议样例。

本增量目标是把系统中的日期级正式日报转换为企业微信日报模板所需的“日期、今日工作内容、明日工作计划”，由当前用户显式触发后提交到其已连接的企业微信账号，并在本地留下可追踪、可判定是否可重试的同步结果。

本功能不使用企业微信官方开放 API，而复用已验证的企业微信文档/日报内部接口。内部接口不属于稳定开放契约，因此实现必须将协议适配、登录凭证和业务编排隔离，接口变化不得破坏本地日报数据。

## 2. 用户与使用场景

- 普通用户在“设置”中连接自己的企业微信账号，应用打开受控登录窗口完成网页登录；登录态按本地用户隔离。
- 用户确认目标日报模板和字段映射；首版每个系统用户只维护一个启用中的同步配置。接收人配置不需要、也不允许用户手动填写——系统在连接/重连时自动从企业微信模板（已提交记录的 `reportvids`，或模板自身配置的审批人）识别，vid 属于企业微信内部标识，用户不应也不需要接触（2026-08-11 修订）。
- 用户在“我的日报”完成日期级归档后，手动点击“同步到企业微信”。
- 系统展示同步中、成功、认证失效、模板变化、重复、结果不确定或明确失败等状态，并允许符合规则的人工重试。
- 管理员不因其角色获得其他用户的企业微信 Cookie、同步配置或日报正文访问权；同步能力遵循现有所有者隔离。

## 3. 功能范围

### 3.1 P0 - 必须实现

1. **企业微信连接**
   - 使用独立、受限的 Electron 登录窗口，不要求用户复制 Cookie。
   - 获取并加密保存完整的、按域和路径区分的 Cookie jar；不依赖脚本中的固定 Cookie 名单。
   - 可显示连接状态、连接账号的非敏感标识、最近校验时间，并支持重新登录和断开连接。

2. **模板和字段配置**
   - 读取目标日报表单结构，识别日期、今日工作内容、明日工作计划三个目标题目。
   - 保存稳定题目 ID、模板 ID、表单 ID、字段映射、接收人配置和结构指纹。
   - 企业微信模板结构变化后必须暂停提交并要求用户重新确认，不能按旧题目 ID 盲目发送。

3. **手动同步日期级正式日报**
   - 只允许同步当前用户拥有且 `daily_report_days.status=archived` 的正式日报。
   - 同步源只读取 `daily_report_days.archive_snapshot_json`，不得重新读取可变模板来重构历史内容。
   - 提交前提供转换预览；首版不在归档或提交日报时自动触发企业微信请求。

4. **动态字段映射**
   - 日期来自 `daily_report_days.work_date`。
   - `core_type=today_work` 和 `PROJECT_LIST` 默认进入“今日工作内容”；`core_type=tomorrow_plan` 默认进入“明日工作计划”。
   - 其他字段按稳定 `field_key` 配置为“今日工作内容”“明日工作计划”或“忽略”；标签只用于展示和首次建议，不作为运行时唯一标识。
   - 未配置且有值的历史字段默认阻止同步并提示补充映射，避免静默丢失。

5. **同步结果与幂等**
   - 保存每次目标同步的状态、尝试次数、目标指纹、载荷指纹、远端非敏感结果 ID 和脱敏错误摘要。
   - 同一日期级正式日报向同一目标表单/模板成功同步后，再次点击只返回既有成功结果，不重复提交。
   - 请求已经发出但无法确认企业微信是否受理时标记“结果不确定”，不得自动重试造成重复日报。

6. **错误反馈**
   - 区分 Cookie 过期、模板结构变化、重复远端日报、网络或协议失败、明确业务拒绝、结果不确定。
   - 日志、错误响应和审计信息不得包含 Cookie、请求头、完整请求体、日报正文或企业微信返回的个人信息集合。

### 3.2 P1 - 重要功能

- 同步历史查询与按状态筛选。
- 在提交前通过企业微信日报列表检查同一模板、同一用户、同一工作日期的可能重复项；无法唯一匹配时提示冲突，不自动覆盖或追加。
- 模板结构重新发现和字段映射差异预览。
- 对明确未被远端接收的可重试失败提供人工重试。

### 3.3 本增量不包含

- 从企业微信导入日报或用企业微信数据覆盖本地日报。
- 同步草稿、已提交但未日期归档的条目，或同步管理员代看的其他用户日报。
- 自动定时同步、提交日报即同步、离线后台队列或无人值守重试。
- 批量补发全部历史日报、多目标模板并行同步、组织级统一 Cookie。
- 企业微信日报附件、“其他事项”等扩展题目；首版只提交日期、今日工作内容和明日工作计划。
- 修改或删除企业微信中已经提交的日报。
- 绕过企业微信登录、验证码、设备确认或其他风控机制。

## 4. 字段转换规则

1. **日期**：取正式日报的 `work_date`，按 `Asia/Shanghai` 业务日期解释，再由协议适配器转换为目标日期题目的实际格式；不得用客户端当前日期替代。
2. **来源顺序**：多篇来源条目沿用正式快照中的固定顺序，即 `submitted_at ASC, daily_report_id ASC`，同一快照每次转换结果必须一致。
3. **项目列表**：每项仅输出工作项目、工作步骤两项到今日工作内容；`PROJECT_LIST` 条目上另有的类别、权重、预计完成时间节点、实际完成时间、责任人、协助人、所需资源支持、实际完成情况及解决措施等业务台账字段只用于本地记录与导出，不进入企业微信同步文本。若日报另有独立的责任人类自定义字段，该字段按配置附加到今日工作分段；目标模板没有独立责任人题目。
4. **普通字段**：文本按原文保留；数字转十进制文本；日期用 `YYYY-MM-DD`；多选按模板选项顺序或快照保存顺序用中文顿号连接。
5. **空值**：不输出空字段标签；如果目标必填题目转换后为空，预检失败且不发起提交。
6. **多来源**：单来源、单字段时可直接输出值；多来源或同一目标包含多个字段时，以来源分段并保留字段标签，避免不同日报内容混在一起。
7. **长度**：优先使用企业微信表单元数据中的长度限制；超限时提示用户调整映射或本地日报，不允许静默截断。

## 5. 业务规则与状态

- 同步记录状态至少包含：`pending`、`syncing`、`succeeded`、`failed`、`auth_required`、`schema_changed`、`duplicate_detected`、`uncertain`。
- 只有 `failed` 且能证明远端未受理的情况可以直接人工重试；`auth_required` 必须重新登录；`schema_changed` 必须重新确认配置；`duplicate_detected` 和 `uncertain` 必须先核对远端结果。
- 应用崩溃或超时遗留的 `syncing` 记录恢复为 `uncertain`，不能恢复为普通失败。
- 同步成功只更新同步记录，不修改本地日期、日报条目、归档快照、周报或导出状态。
- 用户删除规则需把企业微信绑定和配置视为可显式清理的账号配置；存在同步历史时继续按业务记录保护，不做无提示级联删除。

## 6. 验收标准

### 连接与凭证

- Given 用户未连接企业微信，When 点击连接并完成网页登录，Then 系统只显示非敏感连接信息，Cookie 以系统加密能力保存且 SQLite、日志、renderer 存储中均不存在明文副本。
- Given Cookie 已失效，When 用户发起同步，Then 系统不提交日报，记录 `auth_required` 并引导重新登录，本地归档日报保持不变。

### 映射与提交

- Given 一个已归档日期含多篇、多个模板版本和 `PROJECT_LIST` 字段，When 生成同步预览，Then 输出顺序稳定、项目条目正确渲染为工作项目/工作步骤两行、未映射的非空字段被明确提示。
- Given 目标三个题目均有效且必填内容非空，When 用户确认同步，Then 企业微信返回业务成功后记录远端 ID 和 `succeeded`，响应与日志不含正文和 Cookie。
- Given 企业微信模板题目 ID 或类型已改变，When 同步前校验，Then 记录 `schema_changed`，不向旧题目提交数据。

### 重复与失败

- Given 同一正式日报已成功同步到同一目标，When 再次点击，Then 返回既有成功记录且企业微信提交接口调用次数不增加。
- Given 提交请求发出后连接超时且无法确认结果，When 请求结束或应用重启，Then 状态为 `uncertain`，系统不自动重试。
- Given 企业微信明确返回未受理的业务错误，When 用户修复配置后重试，Then 复用原同步目标记录、递增尝试次数，并保留脱敏的最后错误类型。

## 7. 风险与实施前置

- 企业微信内部接口、Cookie 字段、风控和页面结构可能随时变化，无法承诺与官方 API 相同的稳定性；每次发布必须用受控测试账号做真实冒烟。
- 自动化登录不得规避验证码、设备确认或企业安全策略；若企业策略不允许此方式，功能应保持不可用而不是绕过控制。
- 用户提供的真实 HTTP 样例属于敏感开发资料，实施第一步必须建立忽略规则和脱敏 fixture；原始资料不得进入 Git、测试快照、日志或发布包。
- 本节确认的是产品和技术范围，不代表功能已经实现。进入代码实现前，应先完成敏感样例治理并按技术方案的阶段顺序开发。

# 项目列表子列扩展（CR-20260812-01）

`PROJECT_LIST` 条目从 8 个子列扩展为 10 个，固定顺序为：类别、工作项目、工作步骤、权重、预计完成时间节点、实际完成时间、责任人、协助人、所需资源支持、实际完成情况及解决措施。

- `category`（类别）非必填，新建条目默认值为“重要”，允许用户修改或清空。
- `weight`（权重）非必填，新建条目默认值为空字符串。
- `project`（工作项目）和 `content`（工作步骤）继续必填，其余字段继续为自由文本。renderer 新建项目行时，预计完成时间节点和实际完成时间默认“当日”，责任人默认当前登录用户的 `display_name`，实际完成情况及解决措施默认“已完成”；用户可修改或清空这些默认值。
- 未填写任何业务内容且所有字段仍等于上述默认值的初始行，在保存前按空行过滤；只要用户改动任一默认值，该行就保留并按工作项目/工作步骤必填规则校验。
- 历史日报缺少字段时由 Pydantic 补结构默认值：`category` 为“重要”，两个时间字段为“当日”，`completion_notes` 为“已完成”，`weight`/`owner`/`assistant`/`required_resources` 为空字符串。历史 `owner` 不得按当前查看者昵称回填，不修改数据库表结构。
- Excel 导出按上述 10 列顺序展开；企业微信同步仍只输出工作项目、工作步骤，不发送类别、权重或其他本地台账字段。
